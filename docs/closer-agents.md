# ТЗ: диалоговые агенты-клозеры в холодных аккаунтах

Статус: проектирование (код не писать до утверждения). Автор черновика: сессия 19.10.2026.
Относится к панели tg-check. Правило репозитория: любое изменение коммитить и пушить
в `web-refactor`, `main` держать fast-forward.

## 1. Цель

Сейчас холодный аккаунт шлёт по сути **одно** сообщение (вопрос без ссылки,
`draft-messages.py`) + **один** шаблонный второй шаг (`followup.py`: при ответе «да»
отправляет ссылку из `message2.txt`). Дальше диалог ведёт человек.

Нужно превратить холодный аккаунт в **диалогового агента-клозера**: он отвечает тому,
кто откликнулся, **ведёт переписку в характере персоны**, выясняет нужные поля
(что ищет, район, бюджет, срок, готовность к звонку/подписке) и **доводит до целевого
действия** — звонок или вступление в канал — либо передаёт человеку.

Важно (ограничение сверху): это только для **ответивших**. Двусторонний диалог
безопаснее холодного спама — отвечаем тем, кто сам написал.

**Целевой темп (решение 19.10):** 1000 подписчиков в канал Егора за **2–4 месяца**. Для
этого (разделы ниже):
- **полностью копируем автозамену и скоринг референса** (Timur-Khabibulin) — «Скоринг
  кандидатов» и «Автозамена и живучесть»;
- **объём сообщений — среднее между нашей осторожностью и их агрессией** — «Объём сообщений»;
- добавляем **активную DM-воронку** (их dm-send + dm-replies) — без неё 1000 за 2–4 мес не
  выходит, наш пассивный «коммент → профиль → подписка» для такого темпа слишком медленный.
- расчёт — «Расчёт темпа».

## 2. Что переиспользуем (уже есть в коде)

| Компонент | Файл | Что даёт |
|---|---|---|
| Цикл «смотрим ответы» | `followup.py` | Поллинг диалогов (не живые хендлеры — одна сессия, без постоянной активности), быстрый проход 20 верхних / полный 200 раз в сутки, `fetch_dialogs`, `whose`/`recipients` (сопоставление собеседника с нашим лидом) |
| Чтение переписки | `followup.py: read_talk, their_reply` | Вся история от первого ответа; всё, что человек написал после нашего последнего сообщения |
| Состояние диалога | `followup.py: talks/<акк>.json` | Уже хранит переписку по собеседнику (`{last_id, msgs:[[наше,unix,текст]]}`) — расширяем полями/стадией |
| Клиент модели | `llm.py: chat(system, user, max_tokens, temperature) -> text`, `llm.LAST_ERR` | Тот же, что классифицирует ответы и крутит комменты |
| Персоны | `comments.py: personas/<ник>.txt`, поле `acc.persona` | Характер в system-промпт, свой на аккаунт |
| Лид-лог | `comments.py: comment-leads.csv` (колонки как у `leads-log.csv`) | Единый формат лида, легко слить |
| Воронка-планировщик | `admin.mjs: funnelJob` (`FUNNEL_EVERY=2ч`, idle 24ч) | Когда и как часто запускать проход по ответам |
| Анти-заморозка | `tglib: full_rest_left, send_hold_left`, PEER_FLOOD-гейт | Не трогать аккаунт на отдыхе; «без рассылки» — только читать |

Вывод: **движок диалога — это расширение `followup.py`**, а не новый сервис. Меняем
развилку «verdict → фикс-ссылка» на «LLM(персона+цель+история+поля) → контекстный ответ +
обновление состояния».

## 3. Архитектура диалогового движка

Проход (встроить в `followup.py` / отдельный `closer.py`, зовётся из `funnelJob`):

1. Взять диалоги аккаунта, отобрать тех, у кого последнее слово **не наше** и кто наш лид
   (`whose`).
2. Для каждого: собрать историю (`read_talk`) + текущее состояние лида из стора.
3. Один вызов модели → **структурированный ответ** (JSON):
   ```json
   {
     "reply": "текст ответа человеку (или пусто, если отвечать не нужно)",
     "fields": { "район": "...", "бюджет": "...", "срок": "...", "тип": "..." },
     "stage": "qualify | warm | close | done | reject",
     "need_human": false,
     "reason": "коротко почему (для оператора)"
   }
   ```
   Контракт как у `classify()`: до 3 попыток, при не-JSON/сбое — **ничего не шлём**,
   разберём в следующий проход (ссылка/ответ не должны уйти «вслепую»).
4. Применить: если `reply` непустой и шаг разрешён (см. §8) — отправить с человеческой
   задержкой; обновить `fields`/`stage` в сторе; залогировать.
5. `stage=close/reject/need_human` → остановить авто по этому лиду, уведомить оператора.

**Стадии лида:** `new_reply → qualify → warm → close → done` (и ветки `reject`,
`handoff`). Перенос стадий решает модель на основе собранных полей и цели персоны.

## 4. Состояние разговора на лида

Расширить `talks/<акк>.json` (или отдельный `leads-dialog.json`) записью на лида:
```json
{
  "<ключ-лида>": {
    "acc": "a1", "chat_src": "...", "stage": "qualify",
    "fields": { "район": "Академ", "бюджет": "до 6 млн", "срок": "1-2 мес",
                "тип": "1к", "готов_к_звонку": null },
    "turns": 3, "last_id": 12345, "last_our_at": "...",
    "need_human": false, "handoff_reason": "",
    "msgs": [[наше,unix,текст], ...]
  }
}
```
Поля — цель диалога: пока не собрано N обязательных, модель держит стадию `qualify`.
Запись в `comment-leads.csv` (единый формат) при достижении `warm`/`close` — попадает в
панель (Органика → тёплые лиды) и легко сливается с `leads-log.csv`.

## 5. Цель и скрипт в персоне

Персона = `personas/<ник>.txt` (характер) + **цель** (что выяснить → какое действие).
Формат промпта модели:
- system: персона (кто он, тон, недвижка Екб / ВБ) + **цель и правила диалога** +
  список обязательных полей + текущие уже собранные поля + стадия.
- user: последние N сообщений переписки (как `context=15` в комментах).

Два скрипта (разные цели, движок один):
- **Недвижка Егора:** выяснить район/бюджет/срок/тип → предложить **звонок с риелтором**
  (или вступить в канал Егора). Тон как в `followup.py: VERDICT_SYS` — помогает и с
  покупкой, и с продажей/обменом/ипотекой.
- **ВБ-ниша (vtoroy):** своя цель/поля под оффер пользователя.

Правила в промпте (жёстко): без ссылок/промо до согласия (как фильтры `comments.py`:
`AD_RE`/`PROMO_RE`), не дожимать звонком раньше 2–3 полезных реплик, одно сообщение за ход,
по-русски, живо, без клише («как языковая модель» и т.п. — `CLICHE_RE`).

## Активная DM-воронка (копия референса — главный драйвер темпа)

Наш текущий путь к подписке пассивный (коммент → профиль → канал). Для 1000 за 2–4 месяца
добавляем **активную воронку референса**:
- **Кандидаты** — не только ответившие на рассылку, но и те, кто **засветил интерес в чатах**
  (увидели в комментах/обсуждениях), прошедшие скоринг ≥0.6 (ниже).
- **dm-send** — первое касание в ЛС по кандидату, **среднее нас/их по объёму** («Объём
  сообщений»). Без ссылки в первом сообщении (как `draft-messages`/`followup`).
- **dm-replies** — ведение переписки (их цикл «каждые 30 мин»; у нас — проход `funnelJob`,
  2ч/idle 24ч, можно участить до 30–60 мин для активных диалогов): движок §3 отвечает,
  квалифицирует и **дожимает в подписку на канал** (целевое действие).
- Целевое действие ветвится: **подписка в канал** (основная цель 1000) и/или **звонок**
  (горячий лид → хендофф риелтору).

## Скоринг кандидатов (копия референса)

Копируем их скоринг **0..1, порог 0.6**: прежде чем писать/дожимать, оцениваем кандидата.
- Вход: реплика/сообщение человека в чате + контекст + цель ниши.
- Оценка LLM (можно дешёвой моделью) → число 0..1 «насколько это целевой лид».
- **≥0.6 — берём в DM-воронку**, ниже — пропускаем (не жжём аккаунты на холодных/нерелевантных).
- Скор хранить в сторе лида (поле `score`), пересчитывать при новых сообщениях.
- Это резко повышает КПД аккаунтов и снижает жалобы (пишем только тёплым).

## Автозамена и живучесть (копия референса — полностью)

Берём их схему целиком (у нас уже есть база — `reserveTick`/`deadSince`, достроить до их):
- **Резерв по персоне:** пул запасных аккаунтов; у мёртвого забираем **персону** и отдаём
  запасному (он уже есть: `reserveTick` копирует persona). Канал-прокладка та же.
- **Свип автозамены (их 11:00):** раз в день ищем забаненных/замороженных рабочих, меняем
  на резерв, мёртвого ретайрим. (У нас `reserveTick` каждые 5 мин + 24ч grace — оставить,
  добавить суточный свип-отчёт.)
- **Реавторизация из tdata (их 09:00):** раз в день пробуем поднять отозванные сессии из
  сохранённого tdata/зипа, прежде чем списывать в мёртвые.
- **Ротация/выход из забаненных каналов по-человечески:** перед выходом почитать 1–3 батча
  (в ~50% случаев), с паузами — не инста-лив (из `reference_competitor_lessons`).
- **Состояния канала** (их градации отлёжки): `only_comment` (2 сут), `sleep` (1 сут),
  `suspend` (3 сут), `banned`, `format_error`, `not_found` — перенести в стор чатов.
- Философия «терпим и заменяем»: при среднем объёме часть аккаунтов будет гореть — резерв
  и автозамена держат темп, не роняя воронку.

## Объём сообщений (среднее нас и референса)

| Действие | У нас | У референса | Берём (среднее) |
|---|---|---|---|
| Комментарии / аккаунт / сутки | 1–2 | агрессивнее (монитор свежих постов) | **3** |
| Первое касание DM / аккаунт / сутки | рассылка до 15 (разгон 2→5→8→12→15) | 15 (2/прогон) | **15** (разгон чуть быстрее: 3→6→10→15) |
| Касаний за один прогон | — | 2 | **2–3** |
| Ответов подряд в треде | `thread_depth`=3 | тред-ответы | **3** |
| Частота прохода по активным диалогам | `funnelJob` 2ч | каждые 30 мин | **30–60 мин для активных**, 2ч для остальных |

Всё — только в рабочие часы, с человеческими задержками (§ «Анти-бан»), и аккаунт в
активных диалогах шлёт меньше холодных касаний в тот день.

## Расчёт темпа (1000 подписчиков за 2–4 месяца)

Исходя из пула Егора (~8 коммент- + ~7 send-аккаунтов + резерв) и средних объёмов:
- **Коммент-верх:** ~3 × 8 = ~24 коммента/день → несколько прямых подписок/день + поток
  кандидатов в скоринг.
- **DM-воронка:** 15/день × ~10 аккаунтов = ~150 первых касаний/день; после скоринга ≥0.6 и
  dm-replies-дожима ~5–10% доходят до подписки → **~8–15 подписок/день**.
- **Итого ~10–18 подписок/день** → 1000 за **~55–100 дней ≈ 2–3.5 месяца**. Укладывается в
  2–4 мес с запасом; автозамена держит объём, если часть аккаунтов горит.
- Чувствительные точки: реальная конверсия dm→подписка (калибруем на Фазе 1), привлекательность
  канала Егора (контент), доля кандидатов ≥0.6.

## 6. Хендофф человеку

`need_human=true` (модель сама ставит) или триггеры в коде:
- лид «горячий» и готов к звонку/встрече (критичный шаг — деньги);
- враждебность/жалоба/«не пишите» → стоп + 🤝 (как `shake_hands`);
- модель не уверена (`unclear`/сбой парсинга 2 прохода подряд);
- лид отказался от покупки, но не закрыл разговор (как ветка «НЕЯСНО» в `followup.py`:
  «я продаю», «сам риелтор»).

Хендофф = стоп-авто по лиду + уведомление оператору (событие в панель + пометка в сторе).
Оператор добивает руками во вкладке «Результаты»/«Органика».

## 7. Анти-бан (важнейшее)

- **Отвечаем только ответившим** — двусторонний диалог, меньше жалоб, чем холодный спам.
- **Поллинг, не живые хендлеры** (как `followup.py`): без постоянного соединения с одного адреса.
- Человеческие задержки: «читаем» (`read_pause`), «печатает…» по длине (`typing`), пауза
  между лидами (`DELAY_MIN/MAX=180–350с`).
- Только рабочие часы (`WORK_FROM/TO`, `isWorkTime`), в рамках лимитов.
- **Аккаунт в активных диалогах → меньше холодных писем в тот день** (не грузить один акк и
  рассылкой на объём, и перепиской): учитывать число активных диалогов в дневном плане
  рассылки.
- Разнообразие формулировок даёт сама LLM; дедуп по похожести (`SHINGLE_DUP`) переносим и сюда.
- Ограничения как у комментов: `PEER_FLOOD`→пауза 24ч, `USER_DEACTIVATED`→стоп всего акка,
  `FLOOD_WAIT`<2мин→ретрай ×2 (из разбора референса, `reference_competitor_lessons`).
- Прокси-флап (мобильные): не ограничивать аккаунт, ждать/ретрай (как сторож уже делает).

## 8. Авто vs одобрение (гибрид)

- **Квалифицирующие ответы** (стадия `qualify`/`warm`) — авто (с задержками и лимитами).
- **Критичный шаг** (предложение звонка/ссылки, стадия `close`) — **через очередь на
  одобрение** в панели (как `approve_first=50` у комментов и режим «только смотрю» в
  `followup.py`): оператор видит, что собирается отправить агент, и подтверждает.
- Оператор может **перехватить** любой диалог в любой момент (пометка «веду руками» → авто стоп).
- Фаза роста доверия: начинаем с одобрения ВСЕГО, потом авто-квалификация, потом авто до
  момента звонка.

## 9. Фазы внедрения

1. **Фаза 1 — ответы под одобрение.** Движок генерит реплику, но НИЧЕГО не шлёт сам:
   кладёт в очередь панели, оператор одобряет/правит. Нулевой риск автопилота, видно
   качество персоны и диалога. Здесь же **калибруем конверсию** (dm→подписка) — от неё
   зависит, укладываемся ли в 2–4 мес. (Расширение «режима просмотра» `followup.py`.)
2. **Фаза 2 — поля + стадии + скоринг + авто простых шагов.** Извлечение полей в стор,
   стадии, **скоринг кандидатов (0.6)**, автоответы на квалификации; `close`/`dm-send`
   всё ещё под одобрение.
3. **Фаза 3 — активная DM-воронка на полную.** dm-send по скорингу + dm-replies-дожим в
   подписку, авто-закрытие с порогом уверенности, хендофф-триггеры; **автозамена/реавторизация/
   ротация каналов целиком** (досборка поверх `reserveTick`); дашборд воронки и темпа к 1000.

Автозамена частично уже есть (`reserveTick` — замена мёртвых из резерва с переносом персоны);
на Фазе 3 достраиваем до полной схемы референса (суточные свипы, реавторизация из tdata,
человеческий выход из банов, состояния канала).

## 10. Метрики и риски

Метрики (вкладка воронки, по аккаунту и по нише):
- ответивших → в квалификацию → собрано полей → доведено до звонка/подписки → хендофф;
- конверсия по стадиям, среднее число реплик до цели, расход LLM (`llmUsage`), баны/замены.

Риски:
- LLM уходит с темы / даёт обещания → строгий system-промпт + стадии + `close` под одобрение.
- Перегруз одного аккаунта (рассылка+переписка) → лимит активных диалогов, меньше холодных.
- Приватность/данные лида — хранить минимум, не светить номера в логах без нужды.
- Качество зависит от персоны → калибровать на Фазе 1 (одобрение) до авто.
