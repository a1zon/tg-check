## 1. Что это и зачем

**tg-check ищет лидов в Telegram.** Весь инструмент — это конвейер, который ведёт
человека из тематического чата до строки в «тёплой базе»:

```
тематические чаты → сбор людей из них → живые аккаунты (прогрев)
   → мягкое касание (комментарии в чатах + первое личное сообщение)
   → чтение и квалификация ответов (воронка) → горячие лиды
```

1. **Находим чаты.** От нескольких каналов-семян обходим родные рекомендации
   Telegram и отбираем тематические чаты с публичной группой обсуждения.
2. **Собираем людей.** Разбираем участников этих чатов (а где список скрыт —
   авторов сообщений) в общий список потенциальных лидов.
3. **Держим аккаунты живыми.** Новый аккаунт сутки «отлёживается», потом
   постепенно набирает активность (подписки, чтение, реакции, переписка со
   своими) — чтобы выглядеть настоящим человеком, а не роботом.
4. **Мягко касаемся.** Два канала касания: комментарии по делу в тематических
   чатах и первое личное сообщение-вопрос найденному лиду.
5. **Ведём воронку.** Кто ответил — определяем по его же диалогу, ответ
   квалифицирует модель (да / нет / неясно). Согласным уходит второй шаг со
   ссылкой; вся переписка копится для ручного разбора.
6. **Отдаём лиды.** Тёплые (ответили на комментарий) и горячие (ответили «да»)
   — витриной в панели и выгрузкой в CSV.

Везде по тексту: **«первое касание»**, **«аутрич по лидам»**, **«работа с
лидами»** — так называется этап личного контакта. Автоматический поиск горячих
лидов «по таймеру» и сбор по ИНН (ЕГРЮЛ) убраны 16.10 — не работали как надо;
код остался в истории git.

## Последние изменения (октябрь 2026)

Коротко о том, что добавили в последних правках (детали — в соответствующих
разделах):

**24.10 — стабильные адреса, прогрев без номеров, заморозки:**

- **Своя строка Asocks каждому, регионы по профилю (§6).** У каждого аккаунта
  своя постоянная строка мобильного пула KZ; у prod и vtoroy разные регионы
  (`profiles.json → regions`), один пул модемов профили больше не делят.
- **Стабильный адрес важнее уникальности любой ценой (§6).** Уникальность
  сверяется по живым IP (и соседнего профиля); дубль лечится не больше чем 2
  сменами IP в сутки, дальше терпится, но два аккаунта с одного выходного IP
  одновременно не работают никогда. Замороженные свою строку держат и IP не
  занимают.
- **Без прокси к Telegram — никак; страна — на старте и каждые 10 минут (§6).**
  Ни задача, ни вход, ни инструмент не подключится напрямую. Упала задача из-за
  связи или прокси — это пауза, а не сбой аккаунта.
- **Прогрев без номеров (§9).** Контакты по номеру прогрев не добавляет вообще:
  своим пишет только в открытый диалог или по @нику, ник аккаунт заводит себе
  сам. Свежие и защищённые (старые) друг с другом не переписываются; партия
  расходится по дням и часам; каждая попытка идёт в дневной предел, 4 отказа —
  стоп до завтра; первые 14 дней реакции только в каналах.
- **Заморозку видно сразу (§13).** `FROZEN_*` в любой задаче, «user was deleted»
  у получателя, ежедневный SpamBot у читателей; дословный ответ бота хранится
  (`spamRaw`, `spam-log.jsonl`). Текст «по жалобам» убран — его писала панель, а
  не Telegram.
- **Импорт (§5):** один вход на аккаунт, свой IP до первого подключения, чужие
  сеансы по умолчанию не сбрасываются, api_id и устройство продавца — как есть.

**До 21.10:**

- **Самолечение прокси (§6).** Мобильный KZ-порт у Asocks иногда теряет
  закреплённое устройство и начинает отвечать «404 not found in region» — порт
  жив, а IP под ним нет. Сторож прокси теперь оживляет такой порт сам, дёргая
  **его личную** `refresh`-ссылку (раньше дёргал один общий линк, и мёртвый порт
  мог лежать сутками молча).
- **Честный прогресс прогрева (§9).** «День прогрева» и полоса считаются по
  **реальным дням активности** аккаунта, а не по календарю. Простой (лёг прокси,
  пауза) прогресс больше не двигает — полоса стоит, пока аккаунт на деле молчит.
- **Длина прогрева от возраста аккаунта (§9).** По Telegram-id оценивается дата
  регистрации; свежий аккаунт (его и морозит на холодном касании) греется дольше
  (до 12 дней), старый доверенный — быстрее. Подбирается само, можно задать
  вручную на аккаунт. В UI видно «рег ~мм.гггг → N дн.».
- **Честный UI простоя (§9).** На вкладке «Прогрев» прямо показывается, что
  прогрев СТОИТ (баннер «прокси недоступны», пометка у аккаунта), а не рисуется
  движение в пустоту.
- **Единые имена аккаунтов (§5).** Везде аккаунт зовётся так же, как на вкладке
  «Аккаунты» (имя из Telegram), а не коротким служебным id.

## 2. Стек и где работает

Бэкенд — Node без фреймворков. Работа с Telegram — Python-задачи на Telethon
(родной протокол MTProto, без браузера). Интерфейс — HTML/JS без сборки.

| Что | Где |
|---|---|
| Сервер | `root@46.16.15.238` (Москва, Ubuntu), вход по SSH-ключу |
| Панель | `/opt/tg-panel`, пользователь `tgpanel`, служба `tg-panel` |
| Адрес | `https://bqa.egor-kochnev.ru` (nginx → привратник `127.0.0.1:8787`) |
| Локальная копия | `~/Projects/tg-check` (git), выкладывается `deploy/push.sh` |

Версии зафиксированы: Node 20.20, Python 3.14, Telethon 1.45 в `venv-tg/`,
opentele (для tdata) с правкой под 3.14 (`patch-opentele.py`).

**Несколько профилей в одной панели.** `router.mjs` — привратник на 8787
(слушает только `127.0.0.1`): держит по процессу `admin.mjs` на каждый профиль
(основной `8801`, второй `8802`…), спрашивает логин и проксирует запрос в панель
нужного профиля по подписанной куке. У каждого профиля своя папка данных
(`TG_PANEL_DIR`), **код общий** — одно обновление на всех. Куку браузера профилю
не передаёт — вместо неё одноразовый ключ `TG_PANEL_TOKEN`. Заголовок `Origin`
дальше не шлёт (иначе профиль отбил бы любой POST). Управление профилями — только
из основного (`admin:true`); его папку (`.`) удалить нельзя. Чужой профиль не
виден ни в списке, ни по ссылке; папка профиля закрыта `chmod 700`.

## 3. Архитектура: три слоя

```
браузер → router.mjs → admin.mjs → python-задача → Telegram
          привратник    панель       задача        (через прокси)
```

**Панель ничего не делает с Telegram сама.** Она диспетчер: запускает по одной
Python-задаче на аккаунт, читает их вывод построчно и решает, когда звать аккаунт
снова. Последняя строка задачи — `⌁STATE {json}` (сколько сделано, осталось, не
придержал ли Telegram и на сколько) — это её отчёт планировщику. Остальные строки
идут человеку в журнал.

**Состояние живёт в файлах, а не в памяти.** Перезапуск панели не теряет ничего:
кто кого коснулся, у кого кончилась квота, где остановился прогрев — всё в CSV и
JSON рядом с панелью. Поэтому выкладка безопасна, а `auto-run.json` поднимает
работу после перезапуска сам.

**Один аккаунт — одна задача за раз.** Сессия Telethon — это SQLite-файл, два
процесса на одной сессии дают `database is locked`.

**Авторизация запроса** (`admin.mjs`): валидная кука ИЛИ внутренний ключ
привратника (`TG_PANEL_TOKEN`, сверка `timingSafeEqual`). На каждый POST —
проверка `Origin == host` и заголовок `x-panel: 1`. Потолок одновременных задач
`MAX_RUNNING = 6` (`TG_MAX_PARALLEL`): сервер маленький, задача Python ~60–80 МБ.
Рабочее время и лента — по Екатеринбургу (`Asia/Yekaterinburg`, UTC+5).

## 5. Аккаунты и сессии

Реестр — `accounts.json` (через `server/accounts.mjs`). Ключевые поля: `id`,
`title` (номер), `name`/`username`/`phone`/`user_id` (из Telegram), `proxy`,
`proxyOwn` (своя строка Asocks), `proxyPrev` (прежняя), `session`, `authed`,
`importKey` (отпечаток ключа сессии — 16 знаков sha256, не сам ключ), `device`,
`warmFrom`, `prewarmed`, `dailyCap`, `role` (`send`/`warm`/`read` — читатель
поиска лидов), `graduated`, `protect` (защищённый старый аккаунт, §9),
`warmNoDmUntil` (переписка в прогреве выключена до даты), SpamBot
(`spam`,`spamOk`,`spamAt`,`spamUntil`,`spamKind` = `temp`/`perm`/`frozen`,
`spamRaw` — дословный ответ, `spamRecheckAt`/`spamRecheckWhy` — просьба
перепроверить, §13), выезд прокси из страны (`driftCountry`/`driftIp`/`driftAt`,
пишет задача), квота (`quotaUntil`), флуд (`floodUntil`), отдых после заморозки
(`sendHoldUntil`, `fullRestUntil`), профиль (`about`, канал-прокладка `channel*`).
Панель пишет поля точечно (`Object.assign` под замком) — поля, которые ставят
задачи, не теряются.

- **Подключение:** кнопка «Сессия» → архив tdata или `.session` (+JSON
  продавца) → `import-account.py` (opentele `UseCurrentSession` — тот же ключ,
  нового устройства не появляется). Ещё вход по QR (`login-qr.py`) и по коду
  (`login-code.py`) — только аккаунту с прокси, без прокси панель их не заводит.
  При каждом подключении `tglib.connect()` проверяет ключ:
  мёртвый → `authed=false`; живой → обновляет имя/@/телефон/`user_id` и раз в
  сутки аватарку. `isAuthed` смотрит на флаг `authed` (его ставит реальный вход),
  `hasSession` — на файл `.session` (папка профиля создаётся и на пустом окне).
- **«Не вошёл» после массовой загрузки** — обычно не прошло первое подключение
  через мобильный прокси. Повторить «Сессия» тем же архивом: тот же ключ
  второй раз «с нуля» не подключается и ничего не сбрасывает («Импорт по
  шагам» ниже).
- **Роль:** `send` (работа с лидами) или `warm` (только прогрев). `inOutreach(acc)
  = role !== 'warm'` И нет действующего `sendHoldUntil`/`fullRestUntil`. Новый
  аккаунт заводится только на прогрев; прогретый переходит в работу сам (отметка
  `graduated`, один раз; ручной возврат в `warm` уважается) — видно в журнале:
  «прогрев закончен — перешёл в работу».
- **Имя везде одинаковое.** Аккаунт показывается по имени из Telegram
  (`name || title`) — на вкладке «Аккаунты», в прогреве, в подтверждениях.
  Короткий служебный id (a1, c4) в интерфейсе не мелькает.
- **Смена имени/@/аватарки** — `profile.py`. Совет: не всем сразу с одного IP,
  разные фото на разных аккаунтах.
- **Описание и канал-прокладка** (меню «⋯» аккаунта): «Описание профиля» — «о
  себе» (без премиума до 70 знаков, ссылки не нажимаются). «Канал-прокладка» —
  аккаунт создаёт свой публичный канал, закрепляет пост со ссылкой на основной
  канал и ставит канал в профиль (`account.updatePersonalChannel` — бесплатно,
  но только СВОЙ канал). Под ограничением SpamBot каналы создавать нельзя
  (`USER_RESTRICTED`).

**Импорт по шагам** (`import-account.py`, правки 24.10):

1. **Один вход на аккаунт.** Отпечаток ключа пишется в `importKey`. Тот же ключ у
   этого же аккаунта — повторный импорт: файл сессии не переписывается, чужие
   сеансы второй раз не трогаются. Тот же ключ уже лежит у **другого** аккаунта
   (в любом профиле) — стоп до выдачи IP: два клиента на одном ключе Telegram
   видит как `AUTH_KEY_DUPLICATED` и закрывает оба. Значит, перенос «копией +
   переимпорт», пока старая копия на месте, не пройдёт — сначала убрать сессию
   там.
2. **Свой IP — до первого подключения.** Нет прокси — `proxy_buy.own_session()`
   выдаёт свою строку Asocks в регионах профиля (те же проверки, что у кнопки
   «Свой IP», §6) и кладёт её в аккаунт (`proxyOwn=true`, `proxyPrev=""`) и в
   `asocks-sessions.json`. Прокси задан — используется он. Дальше в обоих случаях
   гейт `tglib.require_country` (§6): чужая или неузнанная страна → стоп, сессия
   на диск не ложится, к Telegram не идём (проверка выключена,
   `TG_REQUIRE_COUNTRY=off`, — заданный прокси хотя бы должен отвечать). Пачка
   импортов выдаёт строки по очереди (замок `.own-proxy.lock` на все профили,
   ждём до 15 мин; выдача — от секунд до нескольких минут). Первая выдача новому
   ключу в предел смен IP за сутки не идёт; тот же ключ при стёртом прокси — для
   Telegram смена IP, она в историю пишется. `TG_ALLOW_DIRECT=1` — импорт без
   своей строки, только для отладки.
3. **Чужие сеансы по умолчанию не сбрасываем.** `ResetAuthorizations`
   (`tglib.harden_account`) при импорте не зовётся: у купленной сессии
   авторизации продавца обычно меньше суток (Telegram всё равно ответит
   `FRESH_RESET_AUTHORISATION_FORBIDDEN`), а сброс сразу после покупки и
   повторные входы — главное, чем путь партии 18.10 отличался от выживших (§13).
   Включить — `TG_HARDEN_ON_IMPORT=1`, и тогда один раз на ключ.
4. **Параметры продавца — как есть.** У session+json api_id/api_hash и
   устройство (`device_model`, `system_version`, `app_version`, `lang_code`,
   `system_lang_code`) — продавца, без подмены: сессия работает ровно под тем,
   под чем родилась. У всех наших продавцов это api_id 2040 с публичным хешем
   TDesktop — на нём панель и подключается (`tglib.api_for`: поле аккаунта →
   `tgapi.json` → 2040). Общий `tgapi.json` **не заводить**: он перевёл бы все
   живые сессии на чужой api_id. У tdata строк устройства нет — панель один раз
   закрепляет вариант из `DESKTOP_VARIANTS` и больше его не меняет.

## 6. Прокси и свой IP

**Зачем свой IP.** Если пачка аккаунтов ходит с одного адреса, Telegram видит их
как одну связку — ограничение одному быстро прилетает всем. Поэтому у каждого
аккаунта свой мобильный IP Казахстана.

**Но стабильный адрес важнее уникальности любой ценой.** Asocks сам переводит
метки на соседние модемы, и правило «тот же IP, что у соседа, — сразу меняем» за
19 ч 24.10 дало 59 смен в prod с часовым ритмом у одних и тех же свежих
аккаунтов. Аккаунт, у которого IP меняется каждый час, выглядит хуже, чем
аккаунт, изредка делящий модем с соседом. Отсюда предел смен и правило «с одного
выходного IP одновременно не работаем» ниже.

**Asocks** (оплата за гигабайт, кабинет `my.asocks.com`). Мобильный пул KZ. Из
входов Telegram пропускает рабочий шлюз `190.2.137.56:9999`. Тариф **$3/ГБ**
(трафик в обе стороны, регион на цену не влияет). Модуль — `server/asocks.mjs`;
всё, что нужно разработчику для работы с кабинетом, — в конце раздела.

**Своя строка каждому** (`server/ownproxy.mjs`; при импорте — `proxy_buy.py`, та
же логика на Python). С 23.10 у аккаунтов не порты, а персональные постоянные
строки общего мобильного пула:

```
http://<логин>-pool-mobile-country-KZ-state-<id региона>-session-<8 hex>:<пароль>@190.2.137.56:9999
```

Логин и пароль пула панель берёт из шаблона любого `-pool-` порта кабинета
(`v2/proxy/ports`), id региона — из `v2/dir/countries` + `v2/dir/states` (кэш на
сутки в `asocks-sessions.json → base`). Метка `session-…` случайная; на одной
метке Asocks держит один IP, пропал модем — даёт другой в том же регионе, страна
и регион не меняются.

**Регионы — свои у профиля.** `profiles.json → regions` (папка кода) →
привратник (`router.mjs`) передаёт панели профиля `TG_ASOCKS_REGIONS` → по этим
регионам раскладывают `ownproxy.mjs` и `proxy_buy.py`. Регион закреплён за
аккаунтом, пока он есть в списке профиля; выпал из списка или аккаунт новый —
самый свободный (по записям `assigned` профиля, без замороженных). Убранный из
списка регион меняется, только когда аккаунту и так нужна новая строка —
проактивных переносов нет. Сейчас:

| профиль | регионы Asocks |
|---|---|
| prod (основной) | Almaty, Atyrau Oblysy, Aktyubinskaya Oblast', North Kazakhstan |
| vtoroy | Shymkent, Pavlodar Region |

Так prod и vtoroy не делят один пул модемов. **Karaganda убрана:** замер 24.10 —
8 новых сессий дали там всего 3 разных IP (Almaty — 7), привязанные к ней
аккаунты садились на одни и те же модемы. Без `regions` у профиля берётся
запасной общий список `KZ_REGIONS` (12 регионов, Karaganda в нём ещё есть) —
поэтому регионы профилю задавать всегда.

**Проверка перед выдачей.** Строка годится, если: отвечает; два запроса
`ipinfo` дают один и тот же IP; страна строго KZ (неизвестная — нет); шлюз
пускает `CONNECT` к DC2 Telegram `149.154.167.51:443` (ждём `200`, MTProto не
шлём); такого IP **сейчас** нет у другого аккаунта. Уникальность сверяется по
**живым** IP (данные сторожа, свежие пробы), а не по строкам, и с аккаунтами
соседнего профиля тоже (их снимок старше 2 мин перепроверяется). Замороженные и
выведенные (`ownDormant`: `spamKind=frozen` или `retired`) IP не занимают и в
загрузку регионов не идут. Попыток: 6 в своём регионе, затем по 3 в каждом из ≤3
самых свободных соседних регионов профиля (дубль — только в своём). Выдача одна
за раз на все профили: флаг `busy` в панели + замок `.own-proxy.lock` у импорта
(замки не связаны между собой — окно гонки маленькое, его закроет дедуп ниже).
Прежняя строка — в `proxyPrev`, каждая смена — запись `{at, ip, region, why}` в
`asocks-sessions.json → changes`. Кнопка «Свой IP каждому» в режиме «всем»
замороженных не трогает, её смены идут в историю с причиной «вручную».

**Когда строку меняют сами** (тик раз в минуту, `admin.mjs`):

- **лежит 5+ минут** (`OWN_DEAD_AFTER`) — новая строка, можно в соседнем регионе;
  не вышло — повтор каждые 15 мин;
- **вышла из страны** — по свежим (≤15 мин) данным сторожа или по отметке самой
  задачи: `tglib` пишет `driftCountry/driftIp/driftAt`, и свежая (≤15 мин,
  `OWN_DRIFT_FRESH`) отметка про текущую строку (позже её выдачи) — причина
  «выход из XX». Если сторож уже видит строку снова в KZ на другом IP — выезд
  кончился сам, не трогаем. Можно в соседний регион;
- **дубль** — тот же живой IP, что у соседа. Подтверждается, только если сторож
  перепроверил **обоих** после того, как совпадение заметили (4–8 мин): мобильный
  CGNAT даёт короткие случайные совпадения. Меняется младший: остаются зрелый (в
  работе / выпущен / пришёл поработавшим), затем раньше заведённый (`added`),
  затем тот, кто на этом IP дольше (`ipSince` у сторожа). Только **в своём
  регионе**; не вышло — отступ 15→30→60→120 мин. Если остающийся сам уезжает
  (выход из страны) — второго не трогаем, дубль уйдёт сам;
- **предел — 2 смены IP аккаунту за сутки** (`OWN_DAY_MAX`). В счёт идут все
  смены — лежит, выезд, вручную (история переживает рестарт). Упёрлись — дубль
  больше не лечим, а терпим (одна запись 🌐 в ленту в сутки на аккаунт):
  одновременно с одного IP панель их всё равно не водит. Лежащую строку и выезд
  из страны меняем всегда — без них аккаунт работать не может;
- общее: не чаще раза в час на аккаунт (`OWN_REPLACE_GAP`); пока у аккаунта идёт
  задача или вход на ПК — ждём их конца (задача держит старую строку до конца);
  лежит больше половины своих строк — это шлюз или баланс Asocks, массовую
  замену не делаем (все сессии разом «переехали» бы) и ждём; замороженных и
  выведенных не меняем вовсе — строка остаётся за ними. В профиле меньше двух
  своих строк — автозамены нет.

**Сторож прокси** (`server/proxyguard.mjs`). Живой прокси переопрашивается раз в
4 минуты, лежащий или моргнувший — раз в 30 с: короткий `http`-запрос к
`ipinfo.io` через прокси (~1 КБ, заодно IP и страна; прокси — через окружение,
пароль в списке процессов не светится). Отличает падение самого прокси (не
достучались, `407`/`502`/`503`/`504`, curl-exit≠0, у Asocks — `404` с телом
`Proxy not found in your region`) от ответа сайта любым кодом
(`200`/`403`/`404`/`429` — прокси довёл запрос, значит живой). Две неудачи подряд
(`DOWN_AFTER=2`) — объявляет прокси лежащим: задачи на нём не запускаются,
аккаунтам это сбоем не считается. `429` (rate-limit по общему мобильному IP) — НЕ
падение, прокси трогать нельзя. Пока панель сама меняет IP (`switching()`),
сторож не проверяет — иначе своё же переключение попало бы в журнал как «прокси
лежит». Сторож помнит IP, страну и с какого момента строка на этом IP
(`ipSince`) — по ним работают выдача и замена выше.

**Самолечение мёртвого порта** (dedicated-порты). У dedicated-порта Asocks
закреплённое мобильное устройство иногда уходит из сети — порт жив (`status=1`),
но отвечает `404 Proxy not found in your region`, и до KZ-выхода дело не доходит.
Лечится личной `refresh`-ссылкой **этого** порта
(`/v2/proxy/refresh/<id>?apiKey=…` → Asocks переназначает порту живое
устройство): сторож зовёт `asocks.refreshLinkFor(raw)` (id порта ищется по логину
из строки прокси, он уникален на порт) раз в 2 минуты, пока порт лежит
(`REVIVE_EVERY`). Два живых dedicated-порта на одном IP — сторож сам рефрешит
лишний (не чаще раза в 90 с; 3 рефреша подряд снова на тот же IP — порт «залип»,
🧊 отступ 30 мин); между профилями такие дубли ловит cron `dedup-proxies.py`.
**У своих строк (`-pool-`) перезапуска нет:** refresh-ссылки у них не бывает,
`refreshLinkFor` отдаёт пусто, в ленте ⛔ «перезапуска нет, панель сменит
строку» — лежащую строку меняет замена выше (5 мин). `dedup-proxies.py` свои
строки пропускает; когда кроме них ничего нет, он тихо выходит, не обращаясь к
кабинету.

**Без прокси к Telegram — никак.** `tglib.client_proxy(acc)` при пустом прокси
падает с «не задан прокси — к Telegram не подключаю»; его зовут `make_client` и
`require_country`, поэтому отказ стоит на всех путях: задачи, импорт, вход по QR
и коду, `access.py`, `desktop-pack.py` и служебные `session-live.py`,
`tg-check-number.py`, `tg-native.py` (теперь через `tglib`: у аккаунта панели —
всегда его прокси, его api_id и устройство; у чужой сессии — переданный прокси,
отметка в реестр не попадает). `native-check.py` отдаёт прокси дочернему
`tg-native` через окружение `TG_NATIVE_PROXY`, а не аргументом. Прямой выход —
только нарочно, `TG_ALLOW_DIRECT=1` (отладка, локальный запуск). Панель вторит:
`start()` отказывает Telegram-задачам без прокси (без него можно лишь проверку
прокси и перенос сессии — импорт выдаст свой IP сам) с `pause:true` — автоматика
ждёт, сбой не считает; `/api/accounts/proxy` не принимает пустую строку у
аккаунта с сессией; вход по QR/коду без прокси не заводится; ручные профиль /
канал / фото / поиск чатов отказывают сразу.

**Гейт страны** (`tglib.require_country`, `tglib.guard_exit`).

- **Перед каждым подключением** страна выхода спрашивается по очереди у `ipinfo` →
  `ip-api` → `ifconfig.co` (по 12 с, всё — не дольше ~40 с) через прокси аккаунта;
  пароль прокси уходит `curl` stdin-конфигом (`-K -`), не в argv. Не та страна
  (`TG_REQUIRE_COUNTRY`, по умолчанию `KZ`) — отказ и отметка
  `driftCountry/driftIp/driftAt` (по ней панель меняет свою строку). Страну не
  узнал ни один сервис — тоже отказ (раньше подключались вслепую). `off` —
  проверка выключена.
- **Внутри долгой задачи** — сторож страны: плановая проба раз в 10 минут
  (`EXIT_RECHECK`, ~1 КБ трафика) и обязательно после переподключения Telethon —
  пока страна не подтверждена, запросы задачи ждут. Не узнали — повтор через 2
  мин, не чаще раза в минуту даже при дёргающейся связи, 3 «не узнали» подряд —
  стоп. Чужая страна — связь рвётся сразу (`_sender._disconnect`), дальнейшие
  запросы падают `tglib.ExitDrift`, задача кончается кодом 1 без `STATE`. Смена
  IP внутри KZ задачу не останавливает — строка в журнале. Сторож опирается на
  внутренности Telethon 1.45 (`client._call`, `_sender`); при обновлении Telethon
  сверить.

**Сбой связи — пауза, а не сбой аккаунта** (`NET_FAIL` в `admin.mjs`). Панель
узнаёт его по тексту задачи: «не задан прокси», «прокси сейчас выходит из XX»,
«не узнать, из какой страны…», «прокси посреди задачи вышел из XX», «страну
выхода … не подтвердить», «прокси отказал (…)» и общее «не достучаться до Telegram
по MTProto» / «связь с Telegram оборвана» / отказ переподключения Telethon
(точная причина важнее общей). Дальше:

- автопрогон: без `fails++` и без выбывания, отступ 5→10→20→30 мин, одна строка в
  журнал на причину; удача серию сбрасывает;
- прогрев: действие не списывается, повтор через 10 мин, подряд — вдвое дольше,
  до часа, заметка «нет связи: …»; промежуток между пачками не сгорает;
- SpamBot: не попытка, просьба перепроверить висит, повтор каждые 15 мин;
- поиск лидов (читатели): пауза 5 мин с заметкой «нет связи: …», с поиска аккаунт
  не снимается;
- сами задачи: `draft-messages.py` при обрыве выходит кодом 1 «связь с Telegram
  оборвана» и попытку человеку не засчитывает; прогрев обрыв отказом не пишет.

Обратная сторона: аккаунт с намертво сломанным прокси (HTTP жив, MTProto нет)
больше не выбывает из прогона, а вечно стоит на паузе с «нет связи: …» — его
смотреть руками. Признак ищется по тексту: поменяли формулировки в `tglib` —
поправить `NET_FAIL`.

**Очередь и параллель — по выходному IP.** Ключ аккаунта — его живой IP по
данным сторожа (`ipKey`; пока сторож не опросил — строка прокси, без прокси —
`direct`). Автоматика (прогон, прогрев, читатели, SpamBot) **никогда не водит
двоих с одного выходного IP одновременно**: IP занят — аккаунт пропускается без
засчитанного сбоя; та же проверка стоит в самом `start()`. Ручной запуск — решение
человека, его не держим. Задачи соседнего профиля этот гейт не видит: межпрофильный
дубль разводит только выдача IP. `ownProxyEach()` = у всех разные живые IP →
параллельно до `MAX_RUNNING`. Режим «одна строка на всех» (`ownStringEach()` —
проверка по строкам) или ссылка ротации — строго по одному (`serial`), перед
каждым смена IP и пауза `rotateWait`. Разнос — только для аккаунтов, чей IP
общий (`sharedIps()`): запуски не чаще раза в 20–40 с (`launchHold`), а перед
каждым касанием `tglib.wait_send_gap` ждёт долю паузы `delay` с последнего
касания любого аккаунта с этого же **выходного IP** (`.send-gap.json` в папке
кода — общий для профилей, один модем бывает у prod и vtoroy; замок `fcntl`).
Смену IP по ссылке делаем только перед работой, которая светит аккаунт (касания,
проверка номеров), не перед чтением ответов.

**Для разработчика: всё про Asocks в одном месте.**

- **Ключ API кабинета** — `/opt/tg-panel/asocks.json` → `{"apiKey": "…"}` (папка
  кода, права 600, один на все профили; в git и в архиве выкладки его нет). Сам
  ключ в документы, коммиты и чат не пишем — владелец передаёт его отдельно,
  разработчику с SSH-доступом он доступен в этом файле. Где лежат прочие секреты
  — [HANDOVER.md](HANDOVER.md). Для песочницы — `ASOCKS_API`/`ASOCKS_KEY`
  (поддельный Asocks), на сервере не заданы.
- **API:** `https://api.asocks.com/v2/<метод>?apiKey=<ключ>` — ключ в query,
  поэтому такие ссылки (и refresh-ссылки портов) не логировать. Что зовёт код:
  `user/balance`, `proxy/total-spent-traffic` (учёт раз в 30 мин, только основной
  профиль), `proxy/ports` (порты, расход, шаблон логина пула), `dir/countries`,
  `dir/states?countryId=` (id регионов для строк), `proxy/refresh/<id>`
  (перезапуск модема dedicated-порта); `proxy_buy.py` умеет ещё
  `proxy/create-port` (покупка dedicated-порта — импорт её больше не зовёт).
- **Шлюз** `190.2.137.56:9999` (переопределить — `TG_ASOCKS_GATEWAY`); другие входы
  Asocks Telegram не пропускает. Формат своей строки — выше; IP и страну сторож и
  выдача берут через `http://ipinfo.io/json`, гейт страны — ещё и через `ip-api`,
  `ifconfig.co`.
- **Переменные:** `TG_ASOCKS_REGIONS` (регионы профиля, ставит привратник из
  `profiles.json`), `TG_REQUIRE_COUNTRY` (`KZ` / `off`), `TG_ALLOW_DIRECT=1`
  (только отладка), `TG_ASOCKS_GATEWAY`.
- **Файлы:** `asocks-sessions.json` у каждого профиля свой (`assigned`, `changes`,
  `base`); пишут и Node, и Python — каждый через свой временный файл
  (`.tmp.<pid>` / `.tmp.py<pid>`) и `rename`, Python перечитывает файл прямо
  перед записью и сверяет отпечаток. Формат `assigned[id]` —
  `{session, region, ip, city, org, country, at}`, менять только парой
  `ownproxy.mjs` + `proxy_buy.py`. Учёт — `asocks-usage.jsonl`, `asocks-ports.json`.
- **Правила:** пароль прокси и ключ не класть в argv и журналы — `curl` получает
  прокси через окружение (`http_proxy`/`https_proxy`/`ALL_PROXY`, `no_proxy`
  снят) или stdin-конфиг (`-K -`); строку прокси в тексты ошибок не вставлять
  (только `tglib.proxy_label`). Строку из кабинета вставлять без хвоста
  `:Регион[https://…]` (§18).

**Туннели на сервере** (xray, слушают только `127.0.0.1`): `tunnel-lv` (SOCKS
`10808` / HTTP `10809`) и `tunnel-lv2` (`10810`/`10811`) — оба выходят через один
сервер, IP `193.32.179.223` (Финляндия). Используются для доступа к модели (§15):
с IP сервера OpenRouter отвечает `403`. В комплекты для ПК такие прокси не
попадают (`kit.isLoopbackProxy`).

**Важно про мобильный модем:** он тянет короткие запросы, но почти не тянет
данные (картинка 20 КБ едет ~38 с). Для просмотра аккаунта человеком не годится —
человеку нужен свой VPN (см. §14).

## 7. Поиск тематических чатов

`discover-chats.py` — разовый обход графа рекомендаций Telegram. От каналов-семян
идёт по `channels.GetChannelRecommendations` (бесплатно, свой аккаунт, свой
прокси) вширь на несколько уровней (BFS). Для каждого найденного канала —
проверка гейтов, подошедшие пишутся в `chats.json`. Запускается через панель
(`/api/organic/discover`), лучше с одного аккаунта-искателя.

- Берёт **только каналы с публичной группой обсуждения** (комментарии пишутся в
  неё, резолв по `@нику` — без ника группу не достать).
- Гейты: `min-subs` (дефолт 500), отсев off-topic по `skip_title`, оценка ниши
  моделью (`niche-score ≥ 0.5`; непонятный ответ → 0 = отсев).
- Параметры: `--seeds` (обязателен), `--niche` (обязателен), `--levels 2`,
  `--limit 200`, `--max-seen 1500` (потолок осмотренных), `--dry`.

## 8. Сбор лидов из чатов

`parse-chat.py` разбирает участников групп/каналов тем же аккаунтом и прокси
(родной MTProto). Два режима: `--chat <ссылка>` (один чат) и `--folder <папка>`
(основной: все чаты из папки Telegram, по одному). Пишет сразу после каждого чата
(флуд на пятом не обнулит первые четыре).

- **Кого берём:** только живых людей (боты, удалённые, сам сборщик — мимо).
  `key` человека = `@username`, а без ника — `id:<id>`.
- **Скрытый список** (`participants_hidden` — Telegram отдаёт только админов):
  берём авторов последних `HISTORY=3000` сообщений. Таких людей меньше, чем
  участников (только пишущие), выборка смещена к активным.
- **Два типа ключа.** `@username` — такого лида может коснуться ЛЮБОЙ аккаунт
  панели. `id:<id>` — только нашедший его аккаунт (у каждого свой `access_hash`
  в сессии). `--only-username` берёт только первых (объём меньше, но пишет
  любой).
- **В несколько аккаунтов.** Папку/список панель делит между свободными
  аккаунтами (по одному на прокси; общий прокси — один). Каждый идёт со своего
  места (`--share i/N`), берёт чат, только забронировав его в `claims.json`.
  `members.csv` и `chats.json` пишутся под замком (`*.lock`): без него
  параллельные записи теряли до 2/3 людей.
- Собранные люди уходят в `members.csv` (полный список, для выгрузки) и в
  `chats/results.csv` (очередь аутрича, сразу `tg=true` — они уже в Telegram).

**Два набора лидов** — свойство аккаунта, не всей панели:

| | по номерам | по чатам |
|---|---|---|
| откуда люди | файл с номерами | разбор групп и каналов |
| нужна проверка | да, «есть ли Telegram» | нет, уже там |
| квота контактов | тратится | не тратится (пишем по `@нику`) |
| файлы | `numbers/results/drafts.csv` | те же в `chats/` |

Порядок людей задают `queue-first.txt` (кого раньше всех) и `chat-priority.txt`
(уровни по названию чата-источника) — читаются каждой задачей заново.

## 9. Прогрев аккаунтов

Прогрев делает так, чтобы аккаунт выглядел живым ДО того, как пойдёт касаться
лидов. Три части: библиотека-калькулятор `server/warmup.mjs`, планировщик
`warmTick`/`warmView` в `admin.mjs` и исполнитель `warmup-activity.py` (одно
действие за запуск).

**Лестница по возрасту** (`WARM_PLAN`): день 0 — отлёжка (0 действий), день 1 — 2,
день 3 — 5, день 5 — 9, день 7 — 15. Срок настраивается (2–21 день, по умолчанию
7), лестница сжимается/растягивается (`planFor`), отлёжка всегда ровно сутки.

**Длина прогрева — от возраста аккаунта** (`regDateFromId` / `warmDaysForAge` в
`server/warmup.mjs`). По Telegram-id оценивается дата регистрации (кусочно-линейно
по опорным точкам id→дата), по возрасту выбирается рекомендованный срок прогрева
(`WARM_BY_AGE`: младше 3 мес — 12 дней, <8 — 10, <18 — 8, <36 — 7, старше — 5). Приоритет: ручной `acc.warmDays` → для зрелых общий срок (чтобы не
срезать плато) → по возрасту для греющихся. `warm()` отдаёт `regDate` и `daysSrc`
(`auto`/`manual`/`default`) для показа в панели. Те же опоры и пороги продублированы
в `warmup-activity.py` (`ID_ANCHORS`, `WARM_BY_AGE`, `eff_warm_days`): срок доходит
до самих действий (раньше панель писала «8 дней», а аккаунт грелся по общим 7).
Правятся только парой. Опоры кончаются на 2025-12 — новые id оцениваются
экстраполяцией.

**Честный прогресс — по реальным дням активности** (правка октября 2026). Раньше
«день прогрева» и полоса считались по календарному возрасту
(`floor((now − warmFrom)/24ч)`): пока аккаунт простаивал (лёг прокси, пауза),
календарь шёл и полоса росла впустую — панель показывала «день 3», когда аккаунт
только начал. Теперь:

- `activeDaysMap()` строит `id → набор Екб-дат`, в которые аккаунт **реально**
  что-то делал (успех прогрева `warmup.csv note=ok`, кроме вопроса к SpamBot, ИЛИ
  отправленное/черновик касания `drafts.csv`). Кэш 30 с (панель опрашивает каждые
  2 с, гранулярность суточная). Сам прогрев считает так же (`age_days` в
  `warmup-activity.py`): раньше он шёл по календарю, и партии 18.10 засчитались
  три дня простоя — она раньше времени перешла к переписке.
- `warm()` считает `day`: на отлёжке — 0; дальше — `min(calDay, число активных
  дней с начала текущего прогрева)`. Простой `day` и полосу `pct` не двигает.
  `idleDays = calDay − day` — сколько суток простоя не засчитано (показывается в
  полосе: «день 1 из 7 · 1 дн. простоя не в счёт»).
- **Зрелые аккаунты считаются по календарю.** `mature = graduated===true ||
  role==='send' || prewarmed===true` — такому `day = calDay`. Иначе бурст-касания,
  работа в другом наборе или простой прокси задним числом срезали бы ему дневной
  лимит с плато до ступени разгона. `prewarmed` — «пришёл поработавшим» (в
  `drafts.csv` уже есть успешные касания): `warmFrom = now−10 суток`, в отлёжку не
  загоняем; без флага такой аккаунт завис бы на ранней ступени и не выпускался.
- Активные дни считаются **с начала текущего прогрева** (даты ≥ `warmFrom`):
  сброс `warmFrom` (активация резерва, ручной возврат) честно начинает разгон
  заново — старая история под тем же id не засчитывается.

**Разнос партии** (правка 24.10). Аккаунты одного импорта шли по прогреву в ногу:
18.10 вся партия в один час перешла к переписке — отпечаток фермы. Теперь у
незрелых:

- ступени сдвинуты на 0–2 активных дня (`warm_lag` в Python и `warmLag` в
  `server/warmup.mjs`, одна формула — `sha256(id:lag)`, не скачет): ступень
  выбирается по `day − lag`, прогрев кончается на `lastStep.day + lag` — панель
  выпускает аккаунт в тот же день, что и прогрев в Python;
- у каждого свой час начала дня (`day_start`): 08:00–10:30 по Екб, на каждый день
  свой. До него задача к Telegram не подключается и отдаёт `state` без note —
  панель зайдёт позже, а не «до завтра» (утром у греющихся несколько пустых
  запусков — это они).

Зрелым — без сдвига и без своего часа, день по календарю.

**Честный UI простоя** (`warmView` + вкладка «Прогрев»). У каждого аккаунта —
`proxyDown` (лежит ли его прокси), в шапке — `stalled` (прогрев включён, окно
открыто, но у ВСЕХ прокси лежат) и `partStalled` (у части). Панель показывает это
прямо: баннер «⛔ прогрев стоит: прокси недоступны», в строке аккаунта «⛔ прокси
недоступен — прогрев по нему стоит», полоса помечается «прогресс стоит» — вместо
движения в пустоту.

**Ритм** (`warmTick`, раз в 30 с; при одной строке на всех или ссылке ротации —
только когда в профиле ничего не идёт; аккаунт, чей выходной IP сейчас занят
другим, пропускается): сессия 2–3 действия через 2–4 мин, потом сон 2–4 ч. Одно
действие = один запуск `warmup-activity.py`. Виды действий и суточные вилки
(`caps`, число из вилки фиксируется на день через `sha256(id:дата:kind)` — не
скачет; день — `day − lag`, при другом сроке лестница растягивается `plan_for`):

| кто | реакции | переписка | подписки | группы | боты |
|---|---|---|---|---|---|
| день 1–3 | 2–3 | — | 1–2 | — | 0–1 |
| день 4–6 | 3–5 | 2–3 | 2–3 | 1–2 | 1–2 |
| день 7+ (до выпуска) | 5–7 | 3–5 | 4–5 | 3 | 1–2 |
| прогрет (`TOP_UP`) | 1 | 0–1 | — | — | — |
| в работе, «живой день» / между порциями (`BETWEEN`) | 3–4 | 1–2 | — | — | — |
| после заморозки (`REWARM`) | 3–5 | 2–3 | — | — | — |

Вне лестницы: `nick` (раз в сутки, пока нет @ника) и вопрос к @SpamBot (раз в
сутки первым действием захода).

**Переписка — только со своими и без номеров** (правки 24.10). Партия 18.10 на
«4-й день» разом импортировала номера друг друга (`ImportContacts`) и
переписывалась каждый с каждым — через сутки её морозили подряд. Теперь:

- **Номера прогрев не трогает вовсе** — ни `ImportContacts`, ни контактов, ни на
  какой ступени. Своему аккаунту пишет только в **уже открытый диалог** или **по
  @нику** из реестра (`find_peer`); нужен `user_id` собеседника в реестре. Нет ни
  диалога, ни ника — собеседника пока нет: заход «пусто» уходит в реакцию, а
  переписку 90 мин не выбирают (`DM_IDLE`); осталась только она — `state` без
  note, панель зайдёт позже.
- **Сверка id.** Ник должен вести к `user_id` из реестра. Ведёт к постороннему —
  письмо не уходит, в журнал «чужой ник», до завтра этот ник не трогаем; ника
  больше нет — «ник не найден».
- **@ник аккаунт заводит себе сам** (действие `nick`, `do_nick`; `--what nick`):
  если ника нет, на свой активный день 2–4 и в свой час (начало его дня + 0–180
  мин), не чаще раза в сутки, первым действием захода. 3–5 вариантов из имени
  (транслит, уменьшительные, `имя_фамилия` / `фамилия_имя` / `имяфамилия` / короткое
  имя + фамилия, две цифры — только у поздних вариантов; 5–32 знака, с буквы, без
  `__`), порядок свой у каждого. Проверяет `CheckUsername` с паузами, ставит первый
  свободный (`UpdateUsername`), пишет `username` в реестр и `nick/ok/@ник` в
  журнал. Заняли во время установки — следующий; заняты все — «ники заняты»,
  завтра другие. Замороженному, между пачками, в догреве после заморозки и под
  ограничением — нет.
- **Две группы, через границу не пишут** (`protected`, в JS — `isProtected`).
  Защищённые — `protect:true` (старые аккаунты хозяина, ставится руками в
  `accounts.json`) и все зрелые (`graduated` / `role=send` / `prewarmed`).
  Свежие пишут и отвечают только свежим, защищённые — защищённым (`dm_peers`):
  заморозка партии новичков не должна тянуть за собой старые. Значит, и
  выпущенный из прогрева покупной аккаунт попадает к защищённым.
- **Узкий круг.** Первым аккаунт пишет только 2–3 постоянным собеседникам
  (`partners`: по хэшу пары id, сначала те, кто сам греется, и из другой партии);
  отвечать может любому своему из группы, кто написал. Замороженные в
  собеседники не попадают. Для нормального прогрева в группе нужно хотя бы три
  аккаунта. `warmNoDmUntil` — переписка у аккаунта выключена до даты.

**Пределы и отказы.**

- **В дневной предел идёт каждая попытка**, удачная или нет (`done_today`):
  рискует сам запрос. Не в счёт только заходы без запроса к цели («пусто», «не
  канал»). Неудачи реакций и «предел подписок» теперь тоже пишутся в журнал.
- **4 отказа за день → стоп до завтра** (`FAIL_DAY`, `fails_today`): задача отдаёт
  note «4 отказа за день» и к Telegram больше не подключается, а в заходе, где
  порог перейдён, просит панель спросить SpamBot (`request_spam_recheck`, §13).
  Отказом не считаются: вопрос к SpamBot, «заморожен», «получатель удалён», «чужой
  ник», «ник не найден», «пусто», «без реакций», «ники заняты» и обрыв связи (он
  вообще не пишется в журнал). Флуд и `PEER_FLOOD` — считаются. Прежнее правило «3
  отказа подряд → SpamBot сразу» снято.
- **Цель вычёркивается** (`struck`), только если после отказа аккаунт что-то
  сделал удачно (сам жив — значит, дело в цели). Замороженный перестаёт находить
  живые каналы и ботов и раньше за день вычёркивал по десятку живых; отказы перед
  пометкой «заморожен» и флуд — не в счёт.
- **Реакции первые 14 активных дней — только в каналах** (`CHANNELS_ONLY`): в
  канале реакция анонимна, в группе — на сообщение незнакомого человека и видна
  ему. Цель оказалась группой — «не канал», канал не принимает реакций — «без
  реакций», к ним больше не ходим; не открылся — сегодня не возвращаемся. У зрелых
  дни тоже считаются активные (`active_days`).
- **Мёртвые каналы убраны** из образца `warm-list.default.json` (7: worldtechnews,
  prodrad, palata121, pikabu_best, worldweeknews, globaltimes_ru, euronewsru).
  Рабочие `warm-list.json` профилей образец поверх не копирует — их чистят на
  сервере.
- **SpamBot в прогреве:** с `--recheck` или при висящей просьбе
  (`spam_recheck_pending`) правило «сегодня уже спрашивали» и 30-мин кэш не
  держат; обычный заход закрывает просьбу, только если после неё бота ещё не
  спрашивали.
- **Заморозка посреди захода** (`FROZEN_*` в любом действии) — стоп захода,
  `tglib.mark_frozen(id, …, "warmup")`, note «заморожен»; «получатель удалён» у
  своего — внеплановая проверка получателя (§13).

**«Живой день»** (`warmup.between`): прогрев только 08:00–23:00 по Екб, сессии
1–2 действия через 90–180 с, сон `livelyNap` (остаток действий на день делится на
время до 23:00). Аккаунтам в работе — догрев весь день по потолку `BETWEEN`, по
одному лёгкому действию в глубоком сне между порциями касаний (не посреди
порции, ≥10 мин до следующей, не в отлёжке после флуда).

## 10. Первое касание и воронка

Сердце аутрича — `autoTick` в `admin.mjs` (каждые 3 с). Раздаёт живым аккаунтам
работу, держит паузы, карантин, флуд-паузы и брони (`claims`), работает по двум
независимым наборам (phones/chats) на общем прокси. Если прокси у всех лежит —
ничего не делает.

**Проверка + касание — одна цепочка.** Пока сегодня есть кого касаться, аккаунт
берёт **один** номер → если есть Telegram и человек недавно заходил, сразу пишет
→ берёт следующий. «Проверка номера» технически = «добавить в контакты» — та же
операция, с которой начинается касание, и квота Telegram на неё общая. Поэтому
отдельной большой лестницы проверок нет: проверок в сутки = касаний в сутки
(`checkMax` только опускает планку). По чатам пишут по `@нику` — контакты не
добавляются, квота не нужна.

**Две ступени воронки.**

1. **Первое касание** (`draft-messages.py`, текст `message.txt`/`message-chat.txt`)
   — это **вопрос без ссылки**: ссылку в первом же сообщении незнакомому Telegram
   не любит. `{LINK}` тут не используется.
2. **Второй шаг** (`followup.py`, текст `message2.txt` с `{LINK}`) — уходит
   только тем, кто ответил «да». Отдельная галочка у каждого набора.

**Чтение ответов идёт ВСЕГДА** (`followup.py`, у того, кто уже касался людей) —
независимо от второго шага. Факт ответа определяется по диалогу: последнее
сообщение не наше → человек ответил. Что ответил — решает модель
(`classify`, да/нет/неясно; `temperature=0`). «Нет» — больше не пишем, ставим
реакцию. «Неясно» и сбой модели — не пишем (ссылка не должна уйти отказавшемуся
из-за плохого разбора). Берёт 20 верхних диалогов (новые ответы всегда наверху);
полный проход раз в сутки. Кто ответил — узнаём по ключу журнала, по `@нику` (без
учёта регистра) и по id из `sent-ids.csv`/`members.csv` (контакт после касания
удаляется, номер скрывшего его в диалоге не виден). Вся переписка копится в
`talks/<акк>.json` — вкладка «Результаты».

**Разгон по дню кампании** (`OUTREACH_PLAN`, `server/warmup.mjs`):
2 → с 3-го дня 5 → с 5-го 8 → с 7-го 12 → с 10-го 15. Даже прогретый по возрасту
аккаунт, впервые пошедший касаться лидов, стартует с 2/сутки (иначе PEER_FLOOD на
запуске). День кампании считается от первого касания **после** `restEnd`
(`max(sendHoldUntil, fullRestUntil)`) — после ограничения/заморозки разгон
начинается заново.

**Ритм аккаунта** (настройки вкладки): порция 2 касания, между ними 180–350 с,
после порции сон 40–60 мин. Сон переживает перезапуск (`restoreRest` досыпает по
времени последнего касания из `drafts.csv`). Рабочее окно — 06:00–24:00 по Екб
(ночные сообщения = жалобы на спам); ночью спим до 6:00.

**Сбой не по вине человека — не попытка ему** (`draft-messages.py`, правка 24.10). Если
касание сорвалось не из-за человека, строка в `drafts.csv` не пишется, пока
ничего не ушло (раньше при `MAX_TRIES=3` живой человек выпадал из базы из-за
чужой заморозки):

- **заморозка** (`FROZEN_*` на `ImportContacts`, `SendMessage`…) —
  `tglib.mark_frozen(id, …, "draft-messages:<метод>")`, задача отдаёт
  `stop=quarantine`;
- **сторож страны оборвал связь** (`tglib.ExitDrift`) — исключение уходит наверх,
  код 1 без `STATE`. Если письмо уже ушло, а `ExitDrift` пришёл на очистке
  черновика, строки `sent=true` и `sent-ids` остаются — повторного письма не
  будет;
- **обрыв связи** (запрос висел в момент обрыва или Telethon сдался) — сразу
  выход кодом 1 «связь с Telegram оборвана (…)»; панель считает это сбоем сети
  (§6), а не поломкой аккаунта.

Если в режиме `--send` черновик уже лёг, а письмо не ушло, человек вернётся в
очередь, и черновик положат заново.

**Уникализация** (чтобы одинаковый текст/ссылка не выдали аутрич — Telegram
узнаёт пачку по хэшу, страдают все аккаунты сразу): `tglib.spin()` разворачивает
`{так|или так}` (на каждого свой выбор), `{LINK}` → живой субдомен-зеркало,
который панель (`mirrorTick`) меняет каждые 30–50 касаний (`mirror.json`,
имена — `mirror-names.txt`).

## 11. Комментарии в чатах (мягкое касание)

`comments.py` (действие прогрева `comment`; **по умолчанию выключены**,
выключатель `comments.on`). Прогретый (или простаивающий) аккаунт заходит в 1–3
закреплённых за ним тематических чата, читает новое и, если есть на что ответить
по делу, отвечает одному человеку. Текст пишет модель в образе `comment-persona.txt`,
код жёстко проверяет на рекламу/ссылки/`@ники`/телефоны/штампы/повторы
(похожесть по тройкам слов). **Ссылок в комментариях нет никогда.** Человек,
ответивший на наш комментарий (пошёл разговор), помечается тёплым лидом в
`comment-leads.csv`.

- Настройки — раздел `comments` в `warm-list.json` (образец в
  `warm-list.default.json`): `per_day` [1,2], `approve_first` (50), `max_age_hours`
  (12), `chat_rest_hours` (24), `chats_per_account` (8), `joins_per_day` (1),
  `settle_hours` (24), `model`.
- Чат закрепляется за ОДНИМ аккаунтом и не перекидывается. Аккаунт **не
  комментирует там, откуда берёт людей** для личных касаний (разбирал чат —
  `members.by`, или писал его участникам) — пересчитывается на каждом заходе.
- Первые `approve_first` комментариев ждут одобрения в карточке на вкладке
  «Прогрев» (текст можно поправить). Удалили наш комментарий дважды разным — чат
  у аккаунта выключается насовсем. Чатам нужен публичный `@ник` (без него группу
  не зарезолвить).

## 13. Ограничения Telegram и защита аккаунтов

- **SpamBot:** временное ограничение с датой (`spamKind=temp`, `spamUntil`) или
  бессрочное (`perm`). Аккаунт на карантине до даты, возвращается сам. Отвечать
  тем, кто написал первым, под временным — можно.
- **Квота на контакты** (`ImportContacts` → `retry_contacts`): Telegram не
  говорит, когда вернётся. Панель пишет `quotaUntil`, через 12 ч пробует один
  номер. Реальный потолок ≈ 20–30 добавлений в сутки (скользящие 24 ч).
- **Флуд** (`FloodWait`, `PEER_FLOOD`): пауза ровно на запрошенное, но не меньше
  3 ч (`REST_AFTER_LIMIT`); `PEER_FLOOD` — 12 ч. Это ограничение на уровне
  **аккаунта**: и аутрич, и прогрев того же аккаунта встают (`floodUntil` в
  реестре, `restoreRest` поднимает его при любом старте).
- **Заморозка** (`FROZEN_*` / ответ SpamBot о заморозке): `spamKind=frozen`,
  бессрочный карантин. В поле `spam` — нейтральное `FROZEN_NOTE` («заморожен
  Telegram — снимается только разбаном через @SpamBot/поддержку»); прежнее
  «блокировка по жалобам (ToS)» было шаблоном панели на любую заморозку, а не
  словами Telegram. Дословно сказанное — в `spamRaw` (≤500 знаков; подсказка на
  бейдже карантина и в строках прогрева) и строкой в `spam-log.jsonl` (`kind`
  ok/temp/perm/frozen, источник: `spambot` или задача:метод). Прогрев делает
  замороженному только вопрос к SpamBot раз в сутки (снимут — отметка уйдёт
  сама). Снимается апелляцией в @SpamBot. Свою строку Asocks замороженный держит,
  но его IP занятым не считается и его строку не меняют (§6).
- **Заморозку видно сразу**, а не утром у SpamBot:
  - любая задача, получившая `FROZEN_METHOD_INVALID`, `FROZEN_PARTICIPANT_MISSING`
    или любой RPC с `FROZEN_*` (`tglib.is_frozen_error` — строгая проверка, без
    ложных срабатываний на ники вроде `@frozen_…`), ставит отметку через
    `tglib.mark_frozen(id, raw, source)` — те же поля, что у проверки SpamBot, под
    тем же замком, плюс строка в `spam-log.jsonl` — и останавливает заход. Так
    делают прогрев, первые касания, комментарии (`comments:<метод>`), проверка
    номеров (`tg-check-number`); в задачах поиска лидов (`enrich-*.py`, только на
    сервере) замена ещё не сделана;
  - своему аккаунту не ушло сообщение с «The specified user was deleted»
    (`INPUT_USER_DEACTIVATED`, или у сущности `deleted`) — так другим виден
    замороженный: прогрев просит панель спросить SpamBot **за получателя**
    (`request_spam_recheck`). `USER_DEACTIVATED` (401) — про наш собственный
    аккаунт, не про получателя;
  - 4 отказа за день в прогреве — тоже просьба перепроверить (§9);
  - просьба — поля `spamRecheckAt`/`spamRecheckWhy` (висит, пока `spamRecheckAt`
    новее `spamAt`, `tglib.spam_recheck_pending`). Панель (`spamTick`, раз в 30 с,
    независимо от того, включён ли прогрев) запускает `warmup --what spam
    --recheck` не раньше 10 мин после прошлого ответа бота, в любое время суток, не
    с занятого IP, мимо 30-мин кэша. Бот ответил — просьба снимается; сбой связи —
    не попытка, повтор через 15 мин; после 3 настоящих неудач просьба снимается с
    записью ⚠ в ленту;
  - **читатели** (аккаунты поиска лидов, `role=read`) тоже спрашивают SpamBot раз в
    сутки — 08–23 по Екб, в случайный момент первых полутора часов окна, в паузах
    между их задачами и не с занятого IP. С поиска лидов их это не снимает.
- **Что мы узнали о заморозках** (23–24.10, подробно — [ЗАЩИТА-АККАУНТОВ.md](ЗАЩИТА-АККАУНТОВ.md)).
  Партия 18.10 — 16 купленных RU-авторегов session+json без ника, фото и истории —
  замёрзла волной на 5–6-й день после импорта (признаки у 10 из 16, у 4
  подтверждено SpamBot), **не отправив ни одного холодного сообщения**. Не IP и
  не дубли (старые аккаунты месяц жили на одном порту без заморозок, первые
  замёрзшие сидели на уникальных портах). Не api_id и не устройство (у всех 36
  архивов продавцов api_id 2040 — тот же, что у панели; устройство в реестре
  совпадает с JSON продавца байт в байт у всех 24 сверенных, включая замёрзших).
  «По жалобам» — только шаблон панели. Отличия в коде от выживших когорт: сброс
  чужих сеансов при каждом импорте и повторные входы (часть партии — 3–4 раза за
  50 мин), плюс синхронный переход партии к переписке через номера. Отсюда правки
  импорта (§5) и прогрева (§9). Старые KZ-аккаунты на тех же условиях получают
  только `temp`; холодные касания с аккаунтов такого типа давали заморозку и
  раньше (14–16.10).
- **Два отдыха после заморозки** (ставятся руками, ISO-время): `sendHoldUntil` —
  «без касаний» (`inOutreach=false`, прогрев идёт в режиме `REWARM`);
  `fullRestUntil` — полный (к Telegram не подключается ничто). После любого из них
  разгон касаний начинается заново с 2/день.
- **Свежий аккаунт сутки отлёживается** — главная защита. Аккаунт с ограничением
  в работу не берут вовсе. Перед первой порцией — `spam_check(force=True)` без
  30-минутного кэша.

## 14. Доступ к аккаунту на компьютере человека

Кнопка «На ПК» собирает **комплект** (zip) под ОС (Telegram Desktop).
Модуль — `server/kit.mjs`.

**Три способа положить аккаунт в комплект:**

1. **Отдельный вход** (по умолчанию). Панель заводит аккаунту ВТОРУЮ авторизацию
   (как при входе с нового компьютера) и кладёт её, а не свой ключ. `access.py`
   делает это обменом, которым Telegram логинит по QR (`AcceptLoginToken`) — вход
   создаётся за ~3 с, человек ничего не вводит. Виден в списке устройств и
   **отзывается из панели**. 2FA: если включена, пароль берётся из `cloud.json`
   (`{id: пароль}`), передаётся в `access.py` через окружение `TG_CLOUD_PASS`.
2. **Без прокси** (у человека свой VPN). Моста нет, адрес даёт компьютер человека.
   Нужен, т.к. мобильный прокси не тянет данные (§6).
3. **Ключ панели** (старый способ). Копия tdata самой панели: выйти нельзя
   (отзовётся у панели). Если аккаунт залит как `.session`, tdata собирается из
   живой сессии тем же ключом (`access.py --tdata-current`).

**Пульт** — один архив на несколько аккаунтов (только Windows): меню `Пульт.bat`
и папка `akkaunty/`, каждый аккаунт обычным комплектом в своём окне (своя папка
данных = своё окно, ограничения «3 на окно» нет).

**Мост** (для способов с прокси) — Desktop не шлёт логин/пароль HTTP-прокси
(отвечает 407): Desktop → SOCKS5 `127.0.0.1:18080` без пароля → мост добавляет
авторизацию → прокси аккаунта. Прокси человек добавляет руками один раз
(Settings → Advanced → Connection type → SOCKS5, `127.0.0.1:18080`).

**Очистка** («Убрать аккаунт с компьютера.bat») — закрывает Telegram и мост ЭТОЙ
папки, удаляет tdata/workdir/kit.json и все копии ЭТОГО аккаунта рядом (по номеру
в имени). Выход в самом Telegram для этого нельзя — отзовёт сессию и у панели.
Устройства и отзыв — `access.py --list/--kill`, в окне «На ПК». Детали находок на
Windows (UTM) — в истории правок (`-many`, `return ,$buf`, BOM, запуск `.bat` из
zip и т.д.).

## 15. ИИ (модель)

`llm.py` — тонкий провайдер-агностичный клиент к OpenAI-совместимому
`/chat/completions` через curl (надёжно тоннелит HTTPS через прокси). Одна функция
`chat(system, user, max_tokens, temperature, tries, model)` → текст или `None`
(мягкий фейл, причина в `LAST_ERR`). Настройки — в `.env` (сначала папка профиля,
потом код): `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `LLM_PROXY`, `LLM_BUDGET`.

- Зовут модель: `followup.py` (разбор ответов да/нет/неясно) и `comments.py`
  (комментарии, своя модель `comments.model`, по умолчанию `openai/gpt-6-luna`).
- Имя «провайдер/модель» понимает только агрегатор OpenRouter; у прямого
  провайдера имя сбрасывается в `LLM_MODEL`.
- С IP сервера OpenRouter отвечает `403` — поэтому через `LLM_PROXY` (туннель
  `socks5h://127.0.0.1:10808`, §6). Сменить провайдера = поменять `.env`, код не
  трогать. Цена комментариев ≈ $0.46 за 1000 (100 аккаунтов × 10 в день ≈
  $14/мес).

## 16. Трафик, деньги, нагрузка

Прокси Asocks платный ($3/ГБ), поэтому трафик считается.

- Каждая задача при отключении пишет в `traffic.csv` байты своих соединений с
  прокси аккаунта (`ss -tinp`, фильтр по `host:port`). Запросы мимо прокси
  (к модели) не считаются.
- `server/asocks.mjs` раз в 30 мин (только основной профиль) снимает баланс и
  общий трафик → `asocks-usage.jsonl`; расход в $ — по падению баланса; `summary()`
  считает сутки/7/30 дней, `$/ГБ` и «хватит на N дней» (runway).
- `makeLlmUsage` так же снимает баланс/расход OpenRouter → `llm-usage.json`.

**Замеры** (сервер 2 ядра / ~2 ГБ RAM): привратник + 2 панели 290–330 МБ; задача
~59 МБ пик; одновременно 1–6 задач. Трафик касаний и прогрева — 1–2 МБ/сутки на
аккаунт. После правок октября (экономные проверки, честный прогрев) ожидание ≈
12–15 МБ/сутки на профиль; сверху — сторож прокси (с 4-минутным опросом живых
≈ 0.3 МБ/сутки на строку) и гейт страны (~1 КБ на старте задачи и раз в 10 мин
внутри долгой).

## 17. Выкладка и проверка

```bash
cd ~/Projects/tg-check && bash deploy/push.sh root@46.16.15.238 --code-only
```

- `deploy/push.sh` собирает архив кода (без данных — сверка состава против
  `DATA_GUARD`, чтобы не затереть прод) и перезапускает `tg-panel`. Автоматика
  после перезапуска продолжает сама. В исключения и `DATA_GUARD` входят и новые
  файлы данных: `.own-proxy.lock`, `spam-log.jsonl`, `.send-gap.*`,
  `*.json.tmp.*`.
- **Код на сервере ≠ git.** Поиск лидов (enrich) пока живёт только на сервере:
  там `admin.mjs`, `web/app.js`, `web/index.html`, `draft-messages.py` богаче
  git-копий, плюс `enrich*.py` и `server/enrich.mjs`. `push.sh` всё это затрёт —

  остальное — как обычно, в паузе.
- **Выкладывать парами.** Новый `tglib.py` нужен всем задачам (`require_country`,
  `guard_exit`, `ExitDrift`, `mark_frozen`, `request_spam_recheck`): со старым
  `tglib` импорт и черновики падают на первом же обращении. `admin.mjs`

  старым панель не стартует. Опоры прогрева и формула разноса — в паре
  `warmup-activity.py` + `server/warmup.mjs`.
- **Выкладывать в паузе между задачами** (`running` пуст): иначе оборвётся живая
  задача на аккаунте. Перезапуск трогает ОБА профиля (одна служба). Сон между
  порциями перезапуск не сбрасывает (`restoreRest`), но идущая в этот момент
  задача оборвётся.
- `web/*` читается на каждый запрос — правки интерфейса без перезапуска (поднять
  `?v=rNN` в `web/index.html` от кеша браузера). `*.py` и `kit/*` читаются заново
  на каждый запуск — можно обновить без перезапуска (`scp` → `mv -f` атомарно).
  Node (`admin.mjs`, `server/*`) — только через перезапуск.
- **Песочница** (`tests/sandbox/`, на сервер не выкладывается): `make_profile.py`
  — выдуманный профиль; `run.py <задача.py>` — настоящая задача с подменённым

- **Живой тест без прода**: отдельная копия кода и данных на своём порту

## 18. Грабли и правила

- `accounts.json` пишут и панель, и задачи — руками править только при
  остановленной панели (запись под замком `*.lock`, общим с Python).
- Один выходной IP на нескольких аккаунтах: автоматика водит их строго по
  очереди (§6), реальная параллель — только когда у каждого свой живой IP.
- Без прокси ничего не подключится. Локальный запуск панели или задачи без
  прокси — только с `TG_ALLOW_DIRECT=1`.
- Тот же ключ сессии у двух аккаунтов (копия в другом профиле) — импорт откажет:
  сначала убрать старую копию. Два клиента на одном ключе = `AUTH_KEY_DUPLICATED`,
  Telegram закрывает оба.
- Ключ Asocks, пароли прокси и ссылки с `apiKey` — не в argv, не в журналы, не в
  тексты ошибок (§6, «Для разработчика»).
- Строку прокси из кабинета Asocks вставлять **без хвоста** `:Регион[https://…]`:
  четвёртое поле через двоеточие панель прочтёт как логин/пароль.
- Падение прокси ≠ ошибка сайта: ответ `429`/`403`/`404` означает, что прокси
  довёл запрос — трогать его нельзя.
- Время: сервер UTC; «сутки» лимитов от UTC-полуночи (кроме проверок — скользящие
  24 ч); рабочее время — по Екатеринбургу.
- Окна `prompt/confirm/alert` замораживают страницу и браузерную автоматизацию.
- `pgrep -f "draft-messages.py"` в `ssh '…'` находит сам себя — писать
  `[d]raft-messages.py` или якорить путь.
- «Сессия отозвана» (файл есть, `authed=false`) — Telegram отозвал ключ (чаще
