# tg-check — полная техническая база продукта

Один документ обо всём устройстве. Подробности по отдельным темам — в соседних
файлах: [CODE.md](CODE.md) (как читать код), [HANDOVER.md](HANDOVER.md) (доступы
и передача), [TECH-BASE.md](TECH-BASE.md) (ограничения Telegram подробно).

Секретов здесь нет — только где они лежат. Пароли, ключи и ссылки с `api_key`
в чат не вставлять.

## 1. Стек

Бэкенд — Node без фреймворков. Работа с Telegram — Python-задачи на Telethon.
Интерфейс — HTML/JS без сборки. Модули: аккаунты/сессии, прокси, отправка (два
режима), чтение ответов, прогрев, выдача аккаунта на ПК. Поиск горячих лидов и
сбор по ИНН (ЕГРЮЛ) убраны 16.10 — не работали как надо; код в истории git.

отобьёт любой POST — так уже было).

## 3. Архитектура: три слоя

```
браузер → router.mjs → admin.mjs → python-задача → Telegram
          привратник    панель       задача        (через прокси)
```

**Панель ничего не делает с Telegram сама.** Она диспетчер: запускает по одной
Python-задаче на аккаунт, читает их вывод построчно и решает, когда звать аккаунт
снова. Последняя строка задачи — `⌁STATE {json}` (сколько сделано, осталось, не
придержал ли Telegram и на сколько) — это её отчёт планировщику. Остальные строки
идут человеку в журнал.

**Состояние живёт в файлах, а не в памяти.** Перезапуск панели не теряет ничего:
кто что написал, у кого кончилась квота, где остановился прогрев — всё в CSV и JSON
рядом с панелью. Поэтому выкладка безопасна, а `auto-run.json` поднимает прогон
после перезапуска сам.

**Один аккаунт — одна задача за раз.** Сессия Telethon — это SQLite-файл, два
процесса на одной сессии дают `database is locked`.

## 5. Аккаунты и сессии

- **Подключение:** кнопка «Сессия» → архив tdata или `.session` → `import-account.py`
  (opentele `UseCurrentSession` — тот же ключ, нового устройства не появляется).
  Ещё вход по QR (`login-qr.py`) и по коду (`login-code.py`).
- При каждом подключении `tglib.connect()` проверяет ключ: мёртвый → `authed=false`;
  живой → обновляет имя/@/телефон/`user_id` и раз в сутки аватарку.
- **«Не вошёл» после массовой загрузки** — обычно не прошло первое подключение через
  мобильный прокси. Повторить «Сессия» тем же архивом.
- **Роль:** `send` (в отправке) или `warm` (только прогрев). Прогретый аккаунт
  переходит в отправку сам (отметка `graduated`, один раз; ручной возврат в `warm`
  уважается). Это видно в журнале: «прогрев закончен — перешёл в отправку».
- Смена имени/@ника/аватарки — `profile.py`. Совет: не всем сразу с одного IP,
  разные фото на разных аккаунтах.

## 6. Прокси и смена IP

- Строка прокси у аккаунта: `host:port:user:pass`, `user:pass@host:port`,
  `socks5://…`, со схемой или без (без схемы — HTTP). Разбор — `accounts.parseProxy`.
  Строку из кабинета провайдера с подписью и ссылкой (`…:9999:Название[https://…]`)
  целиком не вставлять: четвёртое «:поле» разбор примет за логин/пароль, молча.
- **Свой прокси у каждого / общий** решает `ownProxyEach()`: у всех строки разные и
  не пустые → параллельно; хоть две одинаковые → «общий IP».
- **Общий прокси ⇒ по очереди** (`serial`), перед каждым при ссылке ротации — смена IP и
  пауза `rotateWait` (10 с). Явная галочка «Параллельно» на общем IP разрешена, но с
  разносом: запуски задач на одном прокси не чаще раза в 20–40 с (`launchHold`, только
  `drafts`/`check`), а перед каждым сообщением `tglib.wait_send_gap` ждёт, пока с
  этого прокси не пройдёт 25–50 % паузы `delay` (минимум 30–45 с) с последнего
  сообщения любого аккаунта (`.send-gap.json`, замок `fcntl`, сдаётся через 15 мин).
  Галочка «⚡ Параллельно» (вкладка чатов) стоит сразу во всех профилях, кроме
  основного (`profileAdmin`, профиль клиента — там пусто, как было); пока рассылка по
  чатам идёт — показывает, как её запустили. Галочка «по очереди» (вкладка номеров)
  сильнее параллели: если стоит она, прогон пойдёт по очереди.
- **Где сейчас что** — §14. Туннели на сервере (xray, слушают только `127.0.0.1`):
  `tunnel-lv` → SOCKS `:10808`/HTTP `:10809`; `tunnel-lv2` (ключ Latvia-key-2) →
  SOCKS `:10810`/HTTP `:10811`. Оба выходят с **одного IP `193.32.179.223`** (один
  сервер `tsyity6si.noijag.ru`, разные входы).
- **Asocks** (оплата за ГБ, `my.asocks.com`): мобильный пул Казахстана, логин вида
  `…-pool-mobile-country-KZ[-state-…]-mode-query` — новый IP почти на каждое
  подключение. Из трёх входов Telegram пропускает только **`190.2.137.56:9999`**
  (`89.38.99.96`, `109.236.82.42` — таймаут до дата-центров); домен `telegram.org`
  режут все, Telethon он не нужен. Логин у входов общий, поэтому Asocks списывает
  трафик на один «порт» — разбивке по портам в кабинете не верить. Тариф «Traffic
  tariff» **$3/ГБ** (старый «Pay as you go» был $6/ГБ за мобильные); считается трафик
  в обе стороны; регион на цену не влияет. API: `/v2/user/balance`,
  `/v2/proxy/total-spent-traffic`, `/v2/proxy/ports`, `/v2/proxy/port-info?id=`,
  `/v2/plan/info`, ключ — query `apiKey`.
- Проверка прокси: `proxy-check.py --account aN` (адрес + доступ к дата-центру
  Telegram), `--ip` — машинно, только выходной IP.
- **Смену IP делаем только перед работой, которая светит аккаунт** (письма и проверка
  номеров), не перед чтением ответов. Промежуток между сменами — не чаще раза в 12
  минут. Каждая смена уводит модем из сети ≈ на минуту (в журнале «прокси лежит»);
  раньше смены впустую перед чтением ответов и были главной причиной «прокси падает».
- **Этот модем тянет короткие запросы (письма панели), но почти не тянет данные**:
  картинка 20 КБ с telegram.org едет ~38 с (299 байт/с), 1 МБ не вытягивает за минуту.
  Для просмотра аккаунта человеком он не годится — человеку нужен свой VPN/прокси.
- Латвийский VLESS-туннель на сервере быстрый (3.6 МБ/с), но слушает только внутри
  сервера — снаружи к нему не подключиться. Поэтому **в комплект для ПК такой прокси
  не пишется** (`kit.isLoopbackProxy`: 127.x/localhost/::1): Telegram на ПК идёт
  своей сетью. Внешний прокси (Asocks) в комплект пишется — и тогда трафик ПК
  (медиа, 50–300 МБ/ч) идёт по платному прокси.

## 7. Отправка сообщений — два независимых режима

Набор получателей («по номерам» / «по чатам») — **свойство аккаунта**, не всей
панели. У каждой вкладки свой состав и свои настройки; режимы заканчиваются и
останавливаются независимо. Общий у них только **прокси** → общая очередь.

**Порядок людей из чатов** — `chat-priority.txt` в папке профиля (читается заново
каждой задачей): строка = уровень, слова ищутся в названии чата, не подошедшие — в
конце; слово с `=` впереди — точное название чата (иначе подстрока). Сортировка в
`draft-messages.py` (`tglib.chat_rank_fn`). У прода с 16.10: 1 — чаты с ответами «да»
(космонавтов, переезд; посчитано `followup.csv` × `members.csv`); 2 — лиды из выгрузки
`boldo-leads/leads_import.csv` (56 человек, заведены в `members.csv` с настоящим
названием чата-источника, `by=import`, чтобы `{chat}` в письме был верным); 3 — 7 чатов
пользователя (Депо, Пионерка, Малахит×2, Изумрудный бор, Утёс, Совушки); 4 —
ипотека/недвижимость; 5 — ЖК/дома; 6 — инвест (1.5 % ответов, 0 «да»). Бэкапы —
`*.bak-leads-2026-10-16`.

**Разбор чатов со скрытым списком участников** (`participants_hidden` — Telegram
отдаёт только админов): `parse-chat.py` берёт авторов последних `HISTORY = 3000`
сообщений (`--history N`), 100 за запрос с паузой 1.5 с. Проверено 16.10: «ЖК МАЛАХИТ |
ЖБИ» — 169 человек с @username на 600 сообщениях. Такие чаты дают меньше людей, чем
участников: только тех, кто писал.

| | по номерам | по чатам |
|---|---|---|
| откуда люди | файл с номерами | разбор групп и каналов |
| нужна проверка | да, «есть ли Telegram» | нет, уже там |
| квота контактов | тратится | не тратится (пишем по @нику) |
| файлы | `numbers/results/drafts.csv` | те же в `chats/` |

- **Состав набирают галочками на вкладках отправки** (не на «Аккаунтах» — там только
  показ). Занятый соседним режимом не выбирается. Состав меняется на ходу: кнопка
  становится «Добавить в работу: N» / «Снять с работы: N». Прогретый аккаунт на
  «только прогреве» можно взять прямо из вкладки — панель спросит и переведёт.
- **Проверка номеров и письмо — одна цепочка:** пока сегодня есть что написать, аккаунт
  берёт **один** номер → если есть Telegram и человек недавно заходил, сразу пишет →
  берёт следующий. Нашёл «нет»/«давно не заходил» — следующий, предел писем не тратит.
  Пачкой проверяет только когда писать нельзя (режим «только проверять», ночь,
  дневной предел выбран).
- **Проверок в сутки = письмам в сутки** (по графику разгона). Поле «потолок проверок»
  только опускает планку, выше дневного предела писем поднять не может.
- **Проверка ответов идёт ВСЕГДА** (`followup.py`, «Смотрит ответы», раз в полчаса у
  того, кто уже писал людям) — независимо от второго шага. Классифицирует ответы
  (да/нет/непонятно) и пишет в `followup.csv` — отсюда «ответили» в Результатах.
  Раньше это было привязано к второму шагу: без него статистика ответов не копилась.
- **Второй шаг (воронка)** — отдельная галочка у каждого режима: ДОСЫЛАЕТ ответившим
  «да» второе письмо со ссылкой. Только это и добавляет галочка; само чтение ответов
  работает и без неё. Текст второго письма общий на панель.
- **Ритм одного аккаунта** (настройки вкладки, по умолчанию): порция `write.limit` = 2
  сообщения, между ними `delay`–`delayMax` = 180–350 с (пауза внутри задачи), после
  порции сон `pause` × (1…1.5) = 40–60 мин. Дневной предел — разгон по дню отправки
  `OUTREACH_PLAN` (`server/warmup.mjs`): 2 → с 3-го дня 5 → с 5-го 8 → с 7-го 12 →
  с 10-го 15. Счётчик дня — от полуночи сервера (UTC = 05:00 Екб).
- **Сон переживает перезапуск**: `restoreRest()` при старте прогона, при возобновлении
  после перезапуска и при добавлении в идущий прогон берёт из `drafts.csv` (обоих
  наборов) время последнего сообщения аккаунта и досыпает ему `pause`. Раньше каждая
  выкладка ставила всем `nextAt=0`.
- **«Смотрит ответы» без второго шага** запускается без `message2.txt` (только читает).
  Сбой запуска посреди сна сна не режет и сбоем не считается.
- **Рабочее время** для писем — 06:00–24:00 по Екатеринбургу (сервер живёт по UTC).
  Ночью спим **до 6:00 по Екб**, а не «до завтра» (иначе аккаунт просыпался в 5 утра
  по Екб = полночь UTC и снова засыпал на весь день — это чинилось).

## 8. Прогрев

Сутки отлёжки, потом постепенный набор. Две лестницы от даты добавления:

- **писем в сутки** — `server/warmup.mjs` (`WARM_PLAN`): 0 (отлёжка) → 2 → 5 → 9 → 15.
- **человеческих действий в сутки** — `warmup-activity.py` (подписки, реакции,
  группы, переписка со своими, боты).

Срок настраивается в панели (2–21 день, по умолчанию 7); обе лестницы
раскладываются на срок, отлёжка в первые сутки не сокращается. Переписываться
аккаунт может **только со своими** (другими аккаунтами этой панели) — для нормального
прогрева нужно хотя бы три. `TOP_UP` — редкий догрев, когда аккаунты уже отработали.

**Ритм прогрева** (`admin.mjs`, `warmTick`, раз в 30 с; на общем IP — только когда
в профиле ничего не идёт): сессия 2–3 действия через 2–4 мин, потом сон 2–4 ч;
«дневной предел прогрева» → проверка через 3–5 ч. Одно действие = один запуск
`warmup-activity.py`. Потолки (`caps`, число из вилки фиксируется на сутки):

| кто | реакции | переписка | подписки | группы | боты |
|---|---|---|---|---|---|
| день 1–3 | 2–3 | — | 1–2 | — | 0–1 |
| день 4–6 | 3–5 | 2–3 | 2–3 | 1–2 | 1–2 |
| прогрет (`TOP_UP`) | 1 | 0–1 | — | — | — |
| в отправке, «живой день» / между пачками (`BETWEEN`) | 3–4 | 1–2 | — | — | — |
| после заморозки, `sendHoldUntil` (`REWARM`) | 3–5 | 2–3 | — | — | — |

Раз в сутки первым действием — вопрос к @SpamBot (кроме режима «между пачками»).
Реакция: канал из своих подписок, «чтение» 5–15 с, отметка прочитанным, в опросе
50 % голос, иначе реакция на один из 20 последних постов. Переписка: сначала ответ
тому, кто дольше ждёт; второе подряд без ответа не шлём; замороженные (`frozen`) в
собеседники не попадают.

**«Живой день»** — настройка профиля `warmup.between` (галочка в «Как слать»):
- прогрев только 08:00–23:00 по Екб, ночью сон до утра;
- сессии 1–2 действия через 90–180 с, сон 40–150 мин: `livelyNap` делит остаток
  действий на сегодня (`state.left` от скрипта) на время до 23:00;
- аккаунтам в отправке — флаг `--lively` → потолок `BETWEEN` весь день;
- **между пачками**: в глубоком сне между порциями (не посреди порции, ≥ 10 мин до
  следующей, не в отлёжке после флуда — `s.floodUntil`) одно действие `--between`
  (только реакция/переписка, без SpamBot, без смены IP), одно на промежуток.
- **Фокус переписки** — `dm_focus` в `warm-list.json` профиля (`{"accounts":["aN"],
  "until": ISO}`): фокусному до 8 сообщений своим в сутки, его собеседникам до 3,
  отвечают ему первыми. Если писать некому (все свои молчат) — вместо пустого
  захода реакция (только в этих новых режимах; у остальных как было).

## 9. Ограничения Telegram

- **SpamBot:** временное ограничение с датой (`spamKind=temp`,`spamUntil`) или
  бессрочное (`perm`). Аккаунт встаёт на карантин до даты и возвращается сам.
  Отвечать тем, кто написал первым, под временным — можно.
- **Квота на контакты** (`ImportContacts` → `retry_contacts`): Telegram не говорит,
  когда вернётся. Панель пишет `quotaUntil`, через 12 ч пробует один номер. Реальный
  потолок этих аккаунтов ≈ 20–30 добавлений в сутки (скользящие 24 ч).
- **Флуд** (`FloodWait`,`PEER_FLOOD`): пауза ровно на запрошенное, но не меньше 3 ч
  (`REST_AFTER_LIMIT`); `PEER_FLOOD` — 12 ч.
- **Заморозка** (ответ SpamBot «Your account was blocked for violations of the Telegram
  Terms of Service…» или ошибка `FROZEN_*`): `tglib.SPAM_BLOCK` / `is_frozen_error` →
  `spamKind=frozen`, `spamOk=false`, бессрочный карантин (`inQuarantine` проверяет
  `frozen`/`perm` раньше даты). Перед первой порцией прогона `spam_check(force=True)`
  — без 30-минутного кэша. Замороженному прогрев делает только SpamBot раз в сутки
  (снимут — отметка уйдёт сама). Снимается апелляцией в @SpamBot (проверено 15.10).
  По наблюдению: морозят свежие аккаунты (Telegram-id ~8.6–8.9 млрд = 2025 г.) на
  первом холодном касании; старые на том же IP получают только `temp`.
- **Отдых после заморозки** — ставится руками в `accounts.json` (ISO-время):
  - `sendHoldUntil` — «без рассылки»: `inOutreach=false`, `start()` не даёт
    `drafts`/`check`, role-API не переводит в отправку, `follow` без `--send`,
    `draft-messages.py` выходит до подключения; прогрев — `REWARM`;
  - `fullRestUntil` — полный: к Telegram не подключается ничто (защита в
    `tglib.connect`, ранний выход в `warmup-activity`/`followup`/`access`, планировщик
    пропускает). Роль одну «ОК» в панели переключить может, отметку — нет.
- **После ограничения SpamBot — сам** (с 16.10): пока ограничение действует,
  аккаунт, снятый прогоном, раз в сутки спрашивает @SpamBot (путь `frozenCheck` в
  `warmTick`, `heldInRun`) — бессрочное больше не висит вечно. Сняли (дата прошла —
  `autoTick`; бот сказал «свободен» после `spamOk=false` — `tglib.spam_check`) →
  `sendHoldUntil` = +3 суток (`REST_AFTER_RESTRICTION` в `tglib.py` и `admin.mjs`),
  если отдых ещё не стоит. После любого `sendHoldUntil`/`fullRestUntil` разгон писем
  заново с 2/день: день рассылки — от первого письма после конца отдыха
  (`restEnd` в `server/warmup.mjs`).
- Классификация ответа: «покупкой не занимаюсь» = **непонятно**, не «нет». Логика
  в `followup.py` (`VERDICT_SYS`).

## 10. Доступ к аккаунту на компьютере человека

Кнопка «На ПК» у аккаунта собирает **комплект** (zip) под ОС (Telegram Desktop).

**Три способа положить аккаунт в комплект** (`server/kit.mjs`, `kitEntries`):

1. **Отдельный вход** (по умолчанию, рекомендуется). Панель заводит аккаунту ВТОРУЮ
   авторизацию — ту же, что появляется при входе с нового компьютера — и кладёт её,
   а не свой ключ. `access.py` делает это обменом, которым Telegram логинит по QR:
   новый клиент просит токен, панель живой сессией подтверждает (`AcceptLoginToken`),
   новый клиент получает собственный ключ, из него `opentele` собирает tdata.
   **Проверено:** вход создаётся за 3 секунды, человек ничего не вводит.
   Такой доступ виден в списке устройств и **отзывается из панели одной кнопкой**;
   человек может спокойно выходить из аккаунта у себя — панели это не мешает.
   **Облачный пароль (2FA):** если на аккаунте включена двухэтапная проверка, новый
   вход без пароля Telegram не завершает (`SessionPasswordNeededError`). Пароль берётся
   из `cloud.json` в папке профиля (`{id: пароль}`), `access.py` сам делает
   `sign_in(password=…)`. Передаётся он в `access.py` через окружение `TG_CLOUD_PASS`
   (не в аргументах и не в URL). Ручного поля ввода в UI нет (убрано) — только хранилище.
2. **Без прокси** (галочка «у человека свой VPN»). Моста нет вовсе, аккаунт
   открывается сразу, адрес даёт компьютер человека. Нужен, т.к. мобильный прокси
   не тянет данные (см. §6).
3. **Ключ панели** (старый способ, галочку снять). Копия tdata самой панели: выйти
   нельзя (отзовётся у панели), убрать можно только стиранием файлов. Если аккаунт
   залит как Telethon-сессия (`.session`), а не tdata (так отдают с маркетплейсов —
   напр. DIP-X: `<номер>_telethon.session`), паковать в комплект нечего. Тогда панель
   делает tdata из живой сессии тем же ключом: `access.py --tdata-current`
   (`opentele` `UseCurrentSession`, без нового входа и без 2FA). Срабатывает, когда
   `zipHasTdata` не нашёл tdata в архиве.

**Пульт** — один архив на несколько аккаунтов (`buildPult`, только Windows). Внутри
меню `Пульт.bat` и папка `akkaunty/`, где каждый аккаунт лежит обычным комплектом.
Меню запускает «Открыть аккаунт» нужной подпапки отдельным окном. **Ограничения «3
аккаунта на окно» нет**: у каждого своя папка данных = своё окно (проверено — три
окна Telegram живут одновременно). В окне скачивания — список «ещё аккаунты в пульт».

**Устройства и отзыв** (`/api/accounts/devices` → `access.py --list/--kill`): в окне
«На ПК» список «Кто имеет доступ к аккаунту» с кнопкой «выгнать» у каждого компьютера
и «выгнать всех, кроме панели». Панель всегда помечена, её не трогаем.

**Мост (для способов с прокси)** — Desktop не шлёт логин/пароль HTTP-прокси (отвечает
407). Поэтому: Desktop → SOCKS5 `127.0.0.1:18080` без пароля → мост добавляет
авторизацию → прокси аккаунта. Мост в комплекте (`kit/bridge.ps1` / `bridge.py`).
Telegram НЕ включает прокси по ссылке `tg://socks` (проверено на 7.2.9) — прокси
человек добавляет руками один раз: Settings → Advanced → Connection type → Use custom
proxy → Add proxy → SOCKS5, `127.0.0.1`, порт 18080, без логина/пароля.

**Очистка** (`kit/clean-win.ps1`, «Убрать аккаунт с компьютера.bat»): закрывает
Telegram и мост ЭТОЙ папки (чужой личный Telegram не трогает), удаляет tdata/workdir/
kit.json (с повторами; упрямые файлы — на удаление при перезагрузке средствами
Windows), **находит и удаляет все копии ЭТОГО аккаунта** рядом, в «Загрузках» и на
рабочем столе (по номеру в имени), включая скачанный архив. Выход в самом Telegram
для этого НЕЛЬЗЯ — отзовёт сессию и у панели.

**Ключевые находки из тестов на настоящей Windows 11 (в виртуалке UTM):**
- Путь с пробелом в имени ломал запуск — PowerShell не брал путь в кавычки, Telegram
  открывался со своей папкой без аккаунта. Это и было «сделал по гайду, не работает».
- Мост падал на каждом соединении Telegram: `return $buf` в PowerShell разворачивал
  массив в поток объектов, `[Net.IPAddress]` его не принимал. Лечится `return ,$buf`.
  Telegram всегда просит адрес цифрами, поэтому мост падал всегда; через домен
  (браузер/curl) работал и выглядел живым.
- Поиск Telegram через `where.exe` ронял скрипт (пишет в stderr + выходит с ошибкой,
  при `ErrorActionPreference=Stop` это обрыв). Добавлен поиск по ярлыку меню «Пуск».
- Чёрное окно больше не исчезает молча: в скрипте ловушка на любую ошибку + пауза.
- Telegram запускается с флагом **`-many`**: без него второй запуск при уже открытом
  Telegram просто передавал фокус старому окну и выходил — со стороны «терминал мигнул
  и ничего не открылось».
- Частая ошибка человека — **запуск `.bat` прямо из zip** (двойной клик внутри архива:
  Windows вытаскивает один `.bat`, без `open-win.ps1` и tdata → «...ps1 does not exist»).
  Теперь все `.bat` это ловят (`if exist …ps1`) и пишут по-русски «распакуй архив».
- `.bat` всегда делает паузу в конце — окно не может молча закрыться.
- Сеть виртуалки/компьютера человека НЕ наследует VPN другого устройства: для «без
  прокси» нужен свой VPN/клиент именно на том компьютере (TUN или SOCKS5 в Telegram).

Все файлы комплекта кладутся с виндовыми переводами строк; `.ps1` и `.txt` — с меткой
BOM (PowerShell 5.1 без неё читает русский как кашу), `.bat` — без BOM. В `.bat` нельзя
метки `goto` (под `chcp 65001` ненадёжны) — ветвление только через `if exist (...) else (...)`.

**Сессии, которые остаются после комплекта.** Каждый комплект с «Отдельным входом» —
новое устройство в Telegram; `access.py` представляет его как «Windows · 10 · Telegram
Desktop 5.7.3», после первого запуска на ПК Telegram переименует его в настоящее
устройство («MacBook Pro M3 Max», «Nitro AN515-57»…). Скрипт «убрать с компьютера»
(`clean-*`) из аккаунта **не выходит** — только удаляет `tdata`/`workdir` (у комплекта
с ключом панели выход выкинул бы и панель). Закрывать устройство — кнопкой «выгнать» в
окне «Комплект» (список устройств, `access.py --kill <hash>` / `--kill-others`) или
«Выйти» внутри Telegram Desktop. 15.10 у тестовых аккаунтов висело 5–10 забытых входов
с 11–13.10 — после каждого комплекта выгонять. Проверка списка устройств без панели:
`account.GetAuthorizationsRequest` с копии файла сессии (не мешает панели).

## 11а. Трафик, деньги, нагрузка

**Учёт трафика** (с 16.10, блок «Трафик и прокси» в «Обзоре», `/api/traffic`):
- каждая задача при отключении (`tglib.aclose` → `_log_traffic`) пишет в `traffic.csv`
  профиля байты своих TCP-соединений **с прокси аккаунта** (`ss -tinp`, фильтр по
  `host:port` прокси — запросы мимо прокси, например к LLM, не считаются). Задачи,
  остановленные SIGTERM без `finally`, строку не пишут; соединения, закрытые раньше
  `aclose`, не видны — цифры по задачам скорее занижены;
- `server/asocks.mjs`: раз в 30 мин (только основной профиль, `DIR === CODE`) снимок
  баланса и `total_spent_traffic` (байты) → `asocks-usage.jsonl`; расход в $ — по
  падению баланса (пополнение пропускается), сутки/7/30 дней, «хватит на N дней».

**Замеры** (15.10, сервер 2 ядра / 1.96 ГБ RAM):

| что | память | CPU | сеть |
|---|---|---|---|
| Node: привратник + 2 панели | 290–330 МБ | 0.1–0.5 % | — |
| xray-туннель | 32 МБ | ~0 | — |
| задача отправки (на аккаунт) | ~59 МБ пик | 0.4–0.6 с | 5–80 КБ |
| действие прогрева | ~60 МБ | ~0.4 с | 2–36 КБ |
| «смотрит ответы» без работы | 27–41 МБ | 0.15–0.2 с | ~0 |
| история чата | — | — | **0.3–0.6 КБ на сообщение** |

Python+Telethon сами по себе 56 МБ. Одновременно: серия — 1 задача; параллель на
общем IP — 1–3; со своими прокси без разноса — N × 59 МБ (19 аккаунтов ≈ 1.1 ГБ —
на грани памяти). Load при работе 0.0–0.33. Трафик отправки и прогрева — 1–2 МБ в
сутки на аккаунт; чат за 3 месяца — ~3 МБ (бойкий 10–15 МБ).

## 12. Выкладка и проверка

```bash
cd ~/Projects/tg-check && bash deploy/push.sh root@46.16.15.238 --code-only
```

- Копирует код (без данных, сессий, `.env`) и перезапускает `tg-panel`. Автоматика
  после перезапуска продолжает сама.
- **Выкладывать в паузе между задачами:** `pgrep -u tgpanel -fc "python.*\.py"` = 0.
  Иначе оборвётся живая задача (константа: «не сломать прогон на акке Егора»).
- `web/*` читается на каждый запрос — правки интерфейса идут **без перезапуска**; но
  браузер кеширует, поэтому при правке `app.js`/`app.css` поднимать `?v=rNN` в
  `web/index.html` и `web/profiles.html` (сейчас r76).
- **Python-задачи (`*.py`, `tglib.py`) и `kit/*` читаются заново на каждый запуск** —
  их можно обновить **без перезапуска службы**: `scp` в `файл.new`, `chown tgpanel`,
  `mv -f` (атомарно — стартующая задача не прочтёт полфайла). Node (`admin.mjs`,
  `accounts.mjs`, `server/*`) — только через перезапуск.
- **Перезапуск перезапускает ОБА профиля** (одна служба). Перед ним смотреть, не идёт
  ли задача, и в каком состоянии прогоны прода. Сон между порциями перезапуск больше
  не сбрасывает (`restoreRest`), но задача, идущая в момент перезапуска, оборвётся.
- `push.sh` не возит данные: исключены сессии, реестры, журналы, `.send-gap.*`,
  `asocks.json`, `asocks-usage.jsonl`, `traffic.csv` и т.д.
- Python-задачи проверяются на «песочнице» (подменённый `tglib.connect`) и на
  виртуалке Windows (UTM, `utmctl exec` без экрана) для комплектов.

## 13. Грабли и правила

- Окна `prompt/confirm/alert` замораживают страницу и браузерную автоматизацию.
- `accounts.json` пишут и панель, и задачи — руками править только при остановленной
  панели.
- Один IP на много аккаунтов: параллель есть, но на общем прокси её гасит разнос
  (`wait_send_gap`) — реальная параллель только когда у каждого свой прокси/IP.
- Строку прокси из кабинета Asocks вставлять **без хвоста** `:Регион[https://…]`:
  четвёртое поле через двоеточие панель прочтёт как логин/пароль.
- Время: сервер UTC; «сутки» лимитов от UTC-полуночи (кроме проверок — скользящие 24 ч);
  рабочее время — по Екатеринбургу.
- VLESS-туннель и логику панели трогать обособленно (константа пользователя).
- `pgrep -f "draft-messages.py"` в `ssh '…'` находит **сам себя** (текст команды
  содержит образец): писать `[d]raft-messages.py` и не упоминать имя файла дальше в
  той же команде, либо якорить `^/opt/…/python`. Так же `pkill` убивал свою ssh-оболочку.
- Роль «только прогрев» снимается одним «ОК» на вопрос «взять в рассылку?» при запуске
  — для защиты аккаунта ставить `sendHoldUntil`/`fullRestUntil`, а не только роль.
- Удалённый получателем «у обоих» чат исчезает и у нас: письмо было, а в папке
  «Рассылка» его нет (пустые диалоги Telegram не показывает).
- Модель для разбора ответов (`llm.py`, OpenRouter) с IP сервера отвечает 403 — ходит
  через `LLM_PROXY` в `/opt/tg-panel/.env` (общий для профилей). С 16.10 это туннель
  `socks5h://127.0.0.1:10808`; раньше был прокси прода, и когда он умер, все ответы
  шли «не разобрал». Проверка: `TG_PANEL_DIR=/opt/tg-panel venv-tg/bin/python llm.py`.
- «Сессия отозвана» (файл есть, `authed=false`) — Telegram отозвал ключ панели; чаще
  всего «завершить другие сеансы» на другом устройстве аккаунта. Нужен новый вход.
- Старая версия QA-сайта — в `_legacy/`, не трогать без спроса.
