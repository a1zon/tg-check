## 1. `admin.mjs` — сервер

### 1.1 «Только проверить» больше не доезжает до набора чатов

`autoStart()`, сразу после вычисления `mode`.

**Было.** Режим (`full`/`check`/`write`) приезжает из общей формы вкладки номеров. Для набора
чатов проверки запрещены (`canCheck` требует `set === 'phones'`, `pickJob`), письма при
`mode === 'check'` тоже запрещены (`canWrite`). При этом условие конца режима считает остаток
через `work(set)`, а тот читает `chats/numbers.csv` — файла у набора чатов нет, `check = 0`,
`need = 0`, и прогон в первом же тике честно объявлял «база пройдена». В журнале это выглядело
как запуск, который ничего не сделал, без единого слова о причине.

**Стало.** Отказ с объяснением и подсказкой, что поставить. Проверка стоит до всей остальной
работы, поэтому состояние прогона не меняется вовсе.

**Риск.** Низкий: отказ виден в интерфейсе (`startAuto` показывает `reason` через `alert`),
затрагивает только нерабочую комбинацию.

### 1.2 «Беречь новые аккаунты» — настройка режима, а не панели

Три места: `auto.opts[set].warm`, `pickJob()` (отлёжка), `autoTick()` (передача задачи).

**Было.** `warm: auto.on ? (auto.warm && o.warm !== false) : o.warm !== false` — при запуске
второго режима значение склеивалось по «И» с уже идущим. Сняв галку на вкладке чатов и запустив
чаты, человек выключал отлёжку и у прогона по номерам, который в этот момент работал: `start()`
проверяет отлёжку только при `warm !== false`, а `pickJob` смотрел на общий `auto.warm`. Свежий
аккаунт (день 0, сутки отлёжки) мог получить задачу. Обратный случай такой же молчаливый:
`warm: false` в базовом наборе после перезагрузки страницы снимал галку, и запуск второго режима
защиту не возвращал.

Дополнительно галка `#warmon` не входила в список полей, запираемых на время прогона, — её
можно было переключить на ходу.

**Стало.** `auto.opts[set].warm = o.warm !== false`; `pickJob` и `autoTick` берут значение
у своего режима (`o.warm`), верхнеуровневый `auto.warm` остаётся только для старых экранов и
ручных задач. В интерфейсе `#warmon` (и `#funnel`) добавлены в список запираемых.

**Что это значит для совместимости.** `auto.warm` больше не «И» по двум режимам, поэтому
прогон, запущенный одним режимом, больше не зависит от второго. `auto-run.json` не меняется:
`warm` и раньше лежал в `raw` каждого режима, так что возобновление после перезапуска панели
поднимает каждый режим со своим значением (было так же).

### 1.3 Пустое числовое поле — это «не задано», а не ноль

`num()`.

**Было.** `Number('') === 0`, результат зажимался в минимум. Очищенное поле «сек между письмами»
(`min="3"`) давало 3 секунды вместо 180, «писем за заход» — 1 вместо 2, «минут отдыха» — 10
вместо 40. Молчаливая подмена ровно в опасную сторону: минимум здесь — максимальная скорость.

**Стало.** Пустое/`null`/`undefined` → значение по умолчанию. Явный ноль по-прежнему зажимается
в минимум (поведение не изменилось).

### 1.4 Запуск второго режима не сбрасывает состояние модема

`autoStart()`, блок `Object.assign(auto, {...})`.

**Было.** `fresh: false, holdUntil: 0, rotateFails: 0` — на каждом запуске. Пока первый режим
ждал подъёма нового адреса (`holdUntil`), запуск второго обнулял паузу: задача могла уйти в
момент переподключения модема и упасть (сбоем аккаунту это не считается — `autoAfter` сначала
спрашивает сторожа — но заход терялся). Там же обнулялся `rotateFails`, счётчик «три неудачи —
останавливаемся»: порог мог не сработать.

**Стало.** Снимок `wasOn` берётся до `Object.assign` (внутри литерала `auto.on` ещё старое
значение), и поля модема сбрасываются только при свежем старте.

### 1.5 Ручной заход идёт по набору открытой вкладки

`start()` (`set0`), `/api/start` (`set` в теле), текст письма.

**Было.** Ручные задачи из блока «Обслуживание» не передавали набор; сервер его не принимал и
брал `baseSet`. Текст первого письма выбирался по `setOf(acc.id)`. Итог: ручной заход с вкладки
чатов мог взять текст «по номерам» и уйти в корневые файлы и брони.

**Стало.** Клиент присылает `set` открытой вкладки, `/api/start` его принимает (только из
`SETS`, иначе как раньше), `start()` считает набор один раз (`opts.set || setOf(acc.id)`) и
использует его и для текста, и для `run(...)`.

### 1.6 Падение тика при завершении одного режима рядом с другим

`autoTick()`, вычисление `queue`. **Это не моя правка, а найденный баг** — всплыл на проверке 1.4.

**Было.** `live` снимается в начале тика, а блок «режим закончился сам» выше по коду вызывает
`finishSet()`, который делает `auto.per.delete(id)`. Дальше сортировка очереди в режиме «по
очереди» читала `auto.per.get(x).lastAt` у уже удалённого аккаунта — тик падал целиком.

Воспроизведение: идут номера (очередь, `serial`), запускаем чаты с пустой базой чатов. Чаты
завершаются сами в том же тике, и ответ на запуск — `{"error":"Cannot read properties of
undefined (reading 'lastAt')"}` вместо `{"ok":true}`. Штатный сценарий «запустил второй режим,
он оказался пустым» на живом сервере (общий прокси ⇒ всегда `serial`).

**Стало.** Сортировка через `?.lastAt`, а очередь дополнительно фильтруется по «аккаунт ещё в
`auto.per` и его набор ещё жив» — иначе можно было запустить задачу набора, который только что
завершился.

**Проверено A/B на чистом `HEAD` и на ветке** (см. §5).

### Что осталось как было (осознанно)

* `serial` «залипает»: второй режим не может ослабить очередь до параллели
  (`serial: (auto.on && auto.serial) || ...`). Через интерфейс недостижимо — галочки
  «Параллельно» жёстко синхронизированы и запираются на время прогона; по API — достижимо.
  Не трогал: правка меняет правила безопасности на общем IP, это решение владельца.
* `#daycap`/`#checkcap` применяются к идущему прогону сразу (так и задумано: это не настройки
  запуска, а потолки на аккаунт), но сохраняются по событию `change`, поэтому «поменял и, не
  убирая фокус, нажал Запустить» отправит ещё старое число. В правки не входило.
* `#voicemode` (голосовое) — одно на оба режима и не восстанавливается после перезагрузки:
  прогон, поднятый из `auto-run.json` с `voice: true`, шлёт голосовые, а галка этого не
  показывает. Отдельная задача, трогает отправку — не в этой ветке.

## 2. `web/app.js` + `web/index.html` — интерфейс

### 2.1 Форма запуска восстанавливается по вкладке

`applyForm()` (бывшая `restoreForm`), `restoreFormFor()`, `paintAuto()`, `showView()`.

**Было.** `restoreForm(a.form)`, где `a.form = autoLastForm(baseSet)` — снимок БАЗОВОГО набора,
один раз за жизнь страницы. Своё у чатов было только «второй шаг» и «Параллельно». Отсюда:
открыл вкладку чатов после номеров → видишь и отправляешь чужие `mode`, `send`, `warm`, лимиты,
паузы и ссылку смены IP; настройки, с которыми чаты запускались в прошлый раз, лежат в
`auto-last.json`, но не показываются нигде.

**Стало.** `formBySet` собирается из `runs[phones].form` / `runs[chats].form` при каждом
опросе состояния. При переходе на вкладку вызывается `restoreFormFor(set)` и подставляет снимок
этой вкладки. Если в форме есть правка, которую человек ещё не запускал (`formTouched`,
навешивается на `input`/`change` полей запуска), снимок не применяется — правка важнее.
Флаг снимается при успешном запуске и при любом применении снимка.

Особый случай — «Второй шаг»: он у каждого режима свой, поэтому `#funnel` всегда берётся из
снимка номеров, а `#cs-funnel` — из снимка чатов, независимо от того, чей снимок сейчас
подставляется. Без этого переход на вкладку чатов переписывал галочку номерам (нашлось
тестом, см. §5).

Выбор «Отправлять/Черновик» при переходах между вкладками не трогается (принудительное
«Отправлять» осталось только на первой загрузке страницы — как и было).

### 2.2 Список запираемых полей и защита от запуска на лежащем прокси

`paintAuto()` и `btn()`.

`#warmon` и `#funnel` добавлены к списку полей, которые запираются на время любого прогона
(они уходят в `/api/auto` при запуске). Если прокси всех выбранных аккаунтов лежит
(`proxyDownLabels`), кнопка запуска запирается и получает подсказку — раньше сервер принимал
запуск (`ok: true`), а тик молча выходил, пока все прокси лежат.

`#daycap`, `#checkcap`, `#voicemode`, `#p-between`, `#cs-between` намеренно НЕ запираются:
первые два и «живой день» применяются к идущему прогону сразу (это их смысл), последние —
настройки следующего запуска.

### 2.3 Убран рудимент `#serial`

Скрытая галочка `#serial` восстанавливалась из формы и выставлялась обработчиком ссылки смены
IP, но в запрос не попадала никогда: `serial` считается как `!parallel`. Удалена из
`index.html` и из `app.js`. Версия ассетов поднята `?v=r86` → `?v=r88`: ключ `r87` уже выложен
из main, поэтому новому `app.js` нужен следующий.

## 3. `deploy/push.sh` — выкладка

**Было.** Список исключений поддерживался руками, и `events.jsonl` (файл ленты «Что
происходит») в нём отсутствовал. Файл создаётся локально при запуске панели на маке, поэтому
уезжал на сервер и обнулял ленту при каждой выкладке. В том же списке не было `.env`,
`auto-run.json`, `auto-last.json`, `base-set.json`, `profiles.json`, `router.json`,
`followup-*.json`, `message-chat.txt`, `mirror*.json`, `chat-priority.txt`. Комментарий «ни
одного файла с данными в списке ниже нет» был неверен, а `.gitignore` тут не защищает: `tar`
пакует рабочую папку, а не индекс git.

Отдельная находка: `chat-priority.txt` — ФАЙЛ-ШАБЛОН в репозитории, а на проде с 16.10 лежит
свой список уровней (документирован в `docs/ПРОДУКТ.md:155-164`, с бэкапами
`*.bak-leads-2026-10-16`). Выкладка затирала бы прод шаблоном. Теперь файл не уезжает — как
`message.txt` и `warm-list.json`, которые остаются на сервере по той же причине.

**Стало.**

1. `EXCLUDES` — массив (тот же смысл, добавлены перечисленные файлы).
2. `DATA_GUARD` — перечень имён данных. `pack()` собирает архив во временный файл, читает его
   оглавление и падает, если в нём есть что-то из `DATA_GUARD`. Забытое исключение теперь
   останавливает выкладку ДО соединения с сервером, а не затирает прод молча.
3. `--dry-run` — собрать архив и проверить состав, никуда не ходя. Нужен для проверки правок
   в списке и для ревью.
4. Порядок шагов и сообщения прежние; отправка на сервер — тот же `tar | ssh tar xzf`.
5. При переносе ветки на свежий main из него взято исключение `./talks` (переписка с
   ответившими) — оно попало в `EXCLUDES` вместе с остальными данными.

**Внимание ревьюеру:** пункт про `chat-priority.txt` меняет поведение выкладки для этого файла.
Если владелец правит приоритет локально и ожидает, что `push.sh` его доставит, — строку нужно
вернуть в `EXCLUDES` и убрать из `DATA_GUARD`.

## 4. Что НЕ сделано и почему

* Раздельные наборы полей формы в HTML (по-настоящему «свои настройки у каждой вкладки»).
  Сейчас один набор элементов на две вкладки, и снимок по вкладке — компромисс без правки
  разметки и запросов. Полное разделение — отдельная работа (index.html + app.js + форма).
* Единая запись о том, что «настройки общие» (подсказка в интерфейсе). Тексты в
  `web/index.html` про общие лимиты остались как были.
* `serial`/`parallel` (см. §1, «осталось как было»).
* Второй прокси и `rotatedRecently()` (глобальный, не по прокси): выстрелит, когда прокси
  станет два, — до тех пор неактуально.
* Документация: `README.md` описывает старую модель «одна общая очередь» и противоречит
  `docs/ПРОДУКТ.md`; `docs/TECH-BASE.md` устарел (прокси, `tg://socks`, вкладка прогрева).
  Правка документации в эту ветку не входит, чтобы ревьюер видел только изменения кода.

## 5. Как это проверялось

Синтаксис: `node --check admin.mjs`, `node --check web/app.js`, `bash -n deploy/push.sh`.

**Панель на выдуманном профиле** (временная папка `TG_PANEL_DIR`, два аккаунта с пустыми
файлами сессий, `set-password`, порт 8899):

* `/api/state` отвечает 200, структура прежняя (`baseSet`, `auto.runs`, `proxy`, …);
* запуск чатов в режиме «только проверить» → отказ с новым текстом (в старом коде запускался
  и мгновенно заканчивался);
* запуск номеров в том же режиме → `{"ok":true}` (то есть отказ не задел законный случай);
* ручной заход `/api/start` с `set` принимается;
* исключений в журнале панели нет.

**A/B на живом поведении** (чистый `git worktree` на `HEAD` против ветки, один и тот же
профиль и сценарий — номера со ссылкой смены IP, затем запуск чатов вторым режимом):

```
до:    hold до второго запуска=58 | ответ на второй запуск={"error":"Cannot read properties of undefined (reading 'lastAt')"} | hold после=0
после: hold до второго запуска=58 | ответ на второй запуск={"ok":true} | hold после=58
```

Это доказывает и §1.4 (состояние модема не сбрасывается), и §1.6 (тик больше не падает).

**Интерфейс — headless Chromium (playwright)**, профиль с РАЗНЫМИ снимками `auto-last.json`
для номеров и чатов. Проверено: номерная вкладка после загрузки показывает свой снимок; переход
на чаты подставляет снимок чатов (режим, отдых, лимиты, пауза IP, «беречь новые», «сек между
письмами»); возврат возвращает снимок номеров; галочка «второй шаг» чужого режима не
переписывается; правка без запуска переживает переход между вкладками; без прогона поля не
заперты. Тест не коммитится (в проекте нет инфраструктуры тестов), но лежит рядом с аудитом и
запускается вручную.

**Выкладка**: `bash deploy/push.sh --dry-run` — «в архиве файлов: 102, данных среди них нет»;
негативная проверка (исключение `./message.txt` убрано на копии скрипта) — выкладка
останавливается с сообщением «в архив попали данные: message.txt».

**После переноса ветки на свежий main всё прогнано заново**: синтаксис (три файла), `--dry-run`
(102 файла, данных нет), панель отвечает `/api/state` 200, новый `/api/talk` из main работает,
отказ по «чатам + только проверить» на месте, UI-тест в headless Chromium зелёный целиком.

**Чего проверка НЕ покрывает** (нужен прогон на тестовом профиле с живой сессией):

* фактическую отправку и выбор текста после §1.5 (ручной заход по набору вкладки);
* поведение отлёжки после §1.2 на настоящем молодом аккаунте;
* ротацию IP с рабочей ссылкой провайдера (в тестах ссылка намеренно нерабочая, порт 9).

## 6. Как откатить

```bash
git revert --no-commit <коммит>       # по одному, если что-то одно
git checkout main -- admin.mjs web/app.js web/index.html deploy/push.sh   # всё сразу
```

Отдельно стоит знать: §1.6 (падение тика) — исправление существующего бага, откат вернёт
ошибку `Cannot read properties of undefined` при запуске второго режима на общем прокси.
